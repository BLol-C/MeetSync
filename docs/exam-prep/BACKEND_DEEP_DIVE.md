เอกสารนี้เสริม `ADVISOR_PREP.md` ในเรื่องที่อาจารย์ถามได้โดยไม่ต้องดูการสาธิต ทุกข้อมูลมาจากการอ่านโค้ดวันที่ 12 พ.ย. 2569 ระบุไฟล์:บรรทัดไว้ให้เปิดดูตาม ผมไม่ได้รันโค้ดหรือเทสต์ใหม่ และส่วนที่ไม่ได้ตรวจเขียนไว้ท้ายไฟล์

## 1. ฐานข้อมูลและวงจรสถานะของประชุม

### 1.1 ตารางและความสัมพันธ์ (`db.py:36-153`)

| ตาราง | เก็บอะไร | จุดที่ควรชี้ |
|---|---|---|
| `users` (`:37`) | บัญชี Google ที่ล็อกอิน และ `calendar_token` | `google_sub` UNIQUE, token Calendar เป็น LONGTEXT ไม่เข้ารหัส |
| `meetings` (`:48`) | หัวข้อ ลิงก์ Meet เวลา สถานะ ประชุมครั้งก่อน | `owner_user_id` และ `previous_meeting_id` เป็น FK แบบ `ON DELETE SET NULL` |
| `speakers` (`:65`) | ผู้เข้าร่วมของประชุมนั้น (ชื่อ อีเมล บทบาท สถานะเข้าร่วม ชื่อแทน) | `UNIQUE (meeting_id, display_name)` (`:77`) ชื่อซ้ำในประชุมเดียวกันไม่ได้ |
| `transcript_segments` (`:81`) | ข้อความที่บอทบันทึกเป็นช่วง | เก็บ `original_text` กับ `text` (ข้อความที่คนแก้) และ `deleted` เป็นธง ไม่ลบจริง |
| `summaries` (`:95`) | รายงานหนึ่งฉบับต่อประชุม | `meeting_id` UNIQUE (`:97`) จึงมีแถวเดียวต่อประชุม เก็บ `model_used`, `prompt_version`, `approved_by`, `approved_at` |
| `agenda_items` (`:109`) | วาระของรายงาน | ผูกกับ `summary_id` |
| `action_items` (`:122`) | งานและกำหนดส่ง พร้อมรหัสนัด Calendar | `google_calendar_event_id`, `google_calendar_link` |
| `summary_versions` (`:141`) | ประวัติทุกรุ่นของรายงาน | เพิ่มแถวอย่างเดียว (คอมเมนต์ `:137-139`) |

ความสัมพันธ์: `users` 1–ต่อ–หลาย `meetings`; `meetings` 1–ต่อ–หลาย `speakers` และ `transcript_segments`; `meetings` 1–ต่อ–1 `summaries`; `summaries` 1–ต่อ–หลาย `agenda_items`, `action_items`, `summary_versions` FK ของลูกส่วนใหญ่เป็น `ON DELETE CASCADE` ลบประชุมแล้วข้อมูลลูกหายตาม

คอลัมน์ `due_date_end`, `invite_sent` ของ `action_items` และ `current_version_no` ของ `summaries` ไม่ได้อยู่ใน `_SCHEMA` แต่ถูกเติมด้วยฟังก์ชัน `_ensure_*` (`db.py:1193-1215`, เรียกจาก `init_schema` `:262-264`)

### 1.2 วงจรสถานะ (`db.py:161-172`)

```
scheduled -> recording -> transcript_review -> transcript_verified -> draft -> approved
                              ^  <-----------------'                   |  ^        |
                              '-- (กลับมาบันทึกต่อ: ->recording)         '--'        '-- ไม่ย้อน ยกเว้นผ่าน reopen_report
```

ตาราง `_STATUS_TRANSITIONS` ระบุสถานะปลายทางที่ไปได้จากแต่ละสถานะ เช่น `transcript_review` ไปได้ทั้ง `transcript_verified` และกลับ `recording` (กรณีบอทหลุดกลางประชุม)

| เปลี่ยนเมื่อ | ทำโดย | ที่มา |
|---|---|---|
| หยุดบอท -> `transcript_review` | `db.end_meeting` | `db.py:496-506` (เงื่อนไข `status = 'recording'` เรียกซ้ำได้) |
| ยืนยัน transcript -> `transcript_verified` | `service.verify_transcript` เรียก `db.set_meeting_status` | `service.py:421-432` (บรรทัด 393 เป็นการแก้ข้อความ ซึ่งทำได้เฉพาะสถานะ `transcript_review`) |
| AI ร่างรายงาน -> `draft` | `generate_report` ต้องอยู่ใน `transcript_verified` หรือ `draft` | `service.py:548-551`, ย้ายสถานะที่ `:569` |
| อนุมัติ -> `approved` | `db.approve_report` | `db.py:1447-1467` |
| ยกเลิกอนุมัติ -> `draft` | `db.reopen_report` | `db.py:1470-1489` |

### 1.3 จุดออกแบบที่อาจารย์ชอบถาม

- **กันสองคำสั่งแข่งกัน:** `set_meeting_status` เช็กและเขียนใน `UPDATE` เดียว (`WHERE status IN ...`) แล้วดู `rowcount == 1` (`db.py:509-529`) ไม่มีช่วงให้สองคำสั่งข้ามขั้นกันได้
- **ทรานแซกชัน:** `_tx()` (`db.py:216-229`) ทำให้งานที่แตะหลายตาราง สำเร็จทั้งก้อนหรือย้อนกลับทั้งก้อน เช่นอนุมัติที่ต้องเปลี่ยนทั้งสถานะประชุมและรายงานพร้อมกัน (`:1451-1467`)
- **`FOUND_ROWS`:** ตั้ง `client_flag=CLIENT.FOUND_ROWS` (`:211-212`) เพื่อให้ `rowcount` นับแถวที่ตรงเงื่อนไข ไม่ใช่แถวที่ค่าเปลี่ยนจริง สำคัญกับการย้าย `draft -> draft`
- **สร้างฐานข้อมูลตอนเริ่ม:** `init_schema` (`:239`) ใช้ `GET_LOCK` ของ MySQL ให้เว็บกับบริการบอทสร้างทีละโปรเซสเมื่อเริ่มพร้อมกัน (`:247-252`)
- **ข้อควรรู้ที่ไม่ตรงกัน:** docstring ของ `init_schema` (`:242`) เขียนว่าไม่มีการอัปเกรดโครงสร้างให้ฐานข้อมูลเก่า แต่โค้ดมีฟังก์ชัน `_ensure_*` เติมคอลัมน์ให้ฐานข้อมูลเก่า ถ้าอาจารย์ถาม ให้ตอบตามโค้ดที่เห็น และไม่อ้างว่ารองรับการอัปเกรดทุกกรณี

## 2. การล็อกอินและสิทธิ์ผู้ใช้

### 2.1 ล็อกอินเว็บ (`ui/auth.py`)
- ใช้ `st.login` แบบ OIDC ของ Streamlit ขอสิทธิ์ระบุตัวตนอย่างเดียว (openid, email, profile) แยกจากสิทธิ์ Calendar ที่ขอตอนกดเชื่อมต่อ (`ui/auth.py:3-4`)
- บันทึกผู้ใช้ด้วย `db.upsert_user` (`ui/auth.py:70`)
- มีโหมดทดสอบ `MEETSYNC_DEV_USER` ที่ข้ามการล็อกอินจริง ใช้ในเทสต์และถ่ายภาพหน้าจอเท่านั้น (`:6-7`, `:44-49`) ห้ามตั้งตอนใช้งานจริง ถ้าอาจารย์ถามว่ามีทางลัดไหม ให้บอกตรงๆ ว่ามีและเป็นข้อควรระวัง

### 2.2 เว็บคุยกับบริการบอท (`bot_service.py:240-264`)
- `identity` (`:242-253`) ตรวจโทเคนลับด้วย `secrets.compare_digest` แล้วอ่าน `user_id` และอีเมลจากหัวข้อ HTTP
- **ข้อสังเกตของผม (วิเคราะห์จากโค้ด ไม่ได้ทดสอบเจาะ):** ผู้ที่มีโทเคนลับระบุ `user_id` ใดก็ได้ในหัวข้อ HTTP ความปลอดภัยจึงพึ่งโทเคนลับและการที่บริการเปิดเฉพาะในเครื่อง (`127.0.0.1:8000` ตาม `ADVISOR_PREP.md` ข้อ "เฉลย") ไม่ได้พึ่งการพิสูจน์ตัวตนต่อผู้ใช้แต่ละคนที่บริการบอท
- `_manager_of` (`:260-264`) ตรวจว่าผู้เรียกจัดการประชุมนั้นได้ก่อนทำคำสั่งบอท

### 2.3 ใครจัดการประชุมได้ (`service.py:36-43`, `db.py:565-584`)
- `meeting_for` ให้ผ่านเมื่อเป็น **เจ้าของประชุม** หรือเป็น **ประธาน/เลขา** ที่อีเมลตรงกัน (เทียบแบบไม่สนตัวพิมพ์) ถ้าไม่ผ่านจะตอบ "ไม่พบการประชุมนี้" เหมือนไม่มีประชุมนั้น เพื่อไม่เปิดเผยว่ามีอยู่จริง
- บทบาทในตาราง `speakers`: `chair`, `secretary`, `attendee`, `guest` (`db.py:174`) ประธานและเลขามีได้คนเดียวต่อประชุม (`:175`)
- ทุกคำสั่งแก้ไขผ่าน `_require_status` (`service.py:46-50`) ที่ตรวจสถานะด้วย: เช่นแก้รายชื่อได้เฉพาะ `EDITABLE_STATUSES` (`service.py:20`) รายงานที่อนุมัติแล้วแก้ไม่ได้

### 2.4 ข้อที่ต้องตัดสินใจเรื่องเอกสาร
ประโยคใน TOR (หัวข้อ 3 เรื่องกลุ่มผู้ใช้) เขียนว่าระบบสิทธิ์เป็นการออกแบบ workflow ยังไม่มีการบังคับสิทธิ์ที่ระดับเซิร์ฟเวอร์ แต่โค้ดตรวจสิทธิ์ที่ชั้น service (`meeting_for`) และที่บริการบอท (`_manager_of`) แล้ว ตามที่อ่านข้างบน ผมไม่ได้แก้ TOR ในจุดนี้ คุณควรตัดสินใจว่าจะปรับถ้อยคำหรือไม่ ก่อนที่อาจารย์จะอ่านเจอและถาม

### 2.5 ถาม-ตอบ
| คำถาม | ตอบ |
|---|---|
| ระบบกันคนอื่นเปิดประชุมของเราได้อย่างไร | ทุกคำสั่งผ่าน `meeting_for` ต้องเป็นเจ้าของหรือประธาน/เลขา ถ้าไม่ใช่ตอบเหมือนไม่มีประชุมนั้น |
| บริการบอทกันคนนอกได้ไหม | ตรวจโทเคนลับ และเปิดในเครื่อง แต่ผมไม่ได้ทดสอบเจาะ จึงไม่รับรองเกินนี้ |
| โทเคน Calendar เก็บอย่างไร | อยู่ใน `users.calendar_token` ไม่เข้ารหัส เป็นข้อจำกัดที่รู้อยู่ |

## 3. ประวัติรายงานและการสร้าง PDF

### 3.1 ประวัติรายงาน
- ชนิดของรุ่น (`db.py:159`): `ai_draft`, `human_edit`, `approve`, `reopen`, `baseline`, `calendar_sync` เก็บเนื้อหาทั้งฉบับเป็น JSON ใน `summary_versions.content`
- AI ร่างใหม่ = รุ่นใหม่ ไม่ทับรุ่นก่อน (`db.py:1399`); คนบันทึกแก้ = รุ่น `human_edit` (ข้ามถ้าเนื้อหาเท่าเดิม `skip_if_same` `:1417`); อนุมัติและยกเลิกอนุมัติก็เป็นรุ่น (`:1466`, `:1489`)
- **ตารางวาระ/งานปัจจุบันเป็นฉบับล่าสุดเสมอ** และ PDF กับ Calendar อ่านจากตารางนั้น ไม่ได้อ่านจาก `summary_versions` (คอมเมนต์ `db.py:139`) ตอนแก้หรือเลือกรุ่นเก่า ระบบลบแล้วใส่วาระและงานของรุ่นนั้นใหม่ (`:1414-1416`, `:1441-1443`) แต่ทำได้เฉพาะฉบับร่างเท่านั้น (`approved_at IS NULL`) อนุมัติแล้วถูกล็อก
- เลือกรุ่นเก่ามาใช้: `use_report_version` (`db.py:1421`) เขียนเนื้อหารุ่นนั้นลงตารางปัจจุบันและย้ายตัวชี้ `current_version_no` ไม่สร้างรุ่นใหม่ ไม่ลบรุ่นใด
- ยกเลิกอนุมัติ (`reopen_report` `:1470`): คืนสถานะ `draft` ล้างผู้อนุมัติและรหัสนัดของทุกงาน (service ลบนัดจาก Google ก่อนแล้วค่อยเรียก)

### 3.2 เทียบรุ่น (`reports/history.py`)
- เทียบข้อความทีละตัวอักษร เพราะภาษาไทยไม่มีช่องว่างคั่นคำ (docstring `:1-5`) ใช้ `SequenceMatcher` (`:22-`)
- ช่วงที่ตรงกันสั้นกว่า 3 ตัวอักษรที่คั่นอยู่ระหว่างส่วนที่ต่าง ถูกรวมเป็นช่วงต่างเดียว (`MIN_EQUAL = 3`) เพื่อไม่ให้ผลเป็นเศษสีสลับถี่
- จับคู่วาระ/งานระหว่างรุ่นด้วยความคล้ายเกิน 0.5 (`SIMILAR`)
- ชื่อชนิดรุ่นแปลเป็นภาษาไทยก่อนแสดง (`KIND_LABEL` `:8-15`) ชนิดที่ไม่รู้จักแสดงเป็น "อื่น ๆ"

### 3.3 PDF (`reports/pdf_report.py`)
- สร้างด้วยไลบรารี FPDF (`class _ReportPDF(FPDF)` `:41`) ฟังก์ชันหลักคือ `build_minutes_pdf` (`:192`)
- ฟอนต์ไทย TH Sarabun New อยู่ในโฟลเดอร์ `fonts/` (ตาม `README.md`) และตัดคำไทยด้วย pythainlp ในไฟล์ `reports/thai_text.py` (ตาม `FILE_GUIDE.md`)
- ผมไม่ได้เปิดอ่านทั้งไฟล์ `pdf_report.py` (433 บรรทัด) รายละเอียดการจัดหน้าอยู่นอกเอกสารนี้

### 3.4 ถาม-ตอบ
| คำถาม | ตอบ |
|---|---|
| รายงานที่ AI ร่างกับที่คนแก้ ต่างกันตรงไหน ดูย้อนได้ไหม | ได้ ทุกรุ่นเก็บใน `summary_versions` เปิดหน้าเปรียบเทียบดูส่วนเพิ่มและลบ |

## 5. Prompt, โมเดล และการคุมเวอร์ชัน

- รายงานแต่ละฉบับเก็บ `model_used` และ `prompt_version` (`db.py:99-100`) ย้อนตรวจได้ว่าฉบับไหนร่างด้วยโมเดลและ prompt อะไร
- prompt อยู่เป็นไฟล์ `prompts/*.md` แยกจากโค้ด ปรับคำสั่งได้โดยไม่แก้โปรแกรม ชื่อที่ใช้อยู่: `minutes_v7` (ประชุมสั้น) และ `minutes_map_v2` (ใช้เมื่อประชุมเกิน 60,000 ตัวอักษร) ตั้งในไฟล์ `reports/summarizer.py` บรรทัด 28-49 (ตาม `FILE_GUIDE.md`) ส่วนโมเดลอ่านจากตัวแปร `GEMINI_MODEL` ใน `.env`
- ประชุมยาวแบ่งเป็นช่วง (`split_chunks`) สกัดบันทึกย่อก่อน แล้วค่อยเรียบเรียงรวม (map-reduce) ตามที่ระบุใน `FILE_GUIDE.md` ตัวเลข "ประมาณ 6 ครั้งต่อรายงาน 3 ชั่วโมง" เป็นการประเมิน ยังไม่ได้ทดสอบกับ 3 ชั่วโมงจริง
- มติเรื่อง prompt: คง `minutes_v7` ไว้ ไม่เปลี่ยนก่อนสาธิต (มติในบทสคริปต์ ซึ่งเป็นบทสมมติ ในโปรเจกต์จริงคุณเป็นผู้ตัดสินใจ)

| คำถาม | ตอบ |
|---|---|
| รู้ได้อย่างไรว่ารายงานฉบับนี้ร่างด้วยอะไร | อ่านคอลัมน์ `model_used` และ `prompt_version` ของตาราง `summaries` |
| ทำไม prompt แยกเป็นไฟล์ | ปรับได้โดยไม่แก้โค้ด และเทียบเวอร์ชันได้ |
| ผลของ AI เหมือนเดิมทุกครั้งไหม | ไม่ ผมเห็นผลต่างกันเมื่อกดร่างซ้ำ จึงมีขั้นตอนให้คนตรวจและมีประวัติรุ่น |

## สิ่งที่ผมไม่ได้ตรวจในไฟล์นี้

- ไม่ได้อ่านเนื้อเทสต์ทุกข้อ คอลัมน์ "ทดสอบอะไร" มาจากชื่อไฟล์ ไม่ใช่การอ่านทีละเทสต์
- ไม่ได้อ่าน `pdf_report.py` ทั้งไฟล์ และไม่ได้ลองสร้าง PDF ใหม่
- ไม่ได้ทดสอบเจาะระบบ ข้อสังเกตเรื่อง `identity` ในข้อ 2.2 เป็นการวิเคราะห์จากโค้ด
- ไม่ได้เปิด `.env` และไม่ได้แตะฐานข้อมูล
- ข้อมูลเรื่อง prompt และ `summarizer.py` อ้างจาก `FILE_GUIDE.md` ที่ผมเขียนไว้ก่อนหน้า ไม่ได้เปิดโค้ดนั้นใหม่ในรอบนี้
