# บอทเข้าห้อง Google Meet ด้วย Playwright: ทำงานอย่างไร และมาจากโค้ดไหน

เอกสารนี้อธิบายตั้งแต่ Playwright คืออะไร ไปจนถึงขั้นตอนที่บอทเข้าห้อง เปิดคำบรรยาย เปิดแผง "บุคคล" และเฝ้าระวัง โดยระบุไฟล์และเลขบรรทัดของโค้ดที่ทำแต่ละขั้น
เลขบรรทัดตรวจจากโค้ด ณ commit `a080b13` (วันที่ 12 พ.ย. 2569) ถ้าแก้โค้ด เลขเลื่อน ให้ค้นด้วยชื่อฟังก์ชัน

ไฟล์หลักที่เกี่ยวข้อง: `bot/meet_engine.py` (เครื่องยนต์บอท), `bot_service.py` (บริการที่คุมบอทและเขียนลง DB), `bot/botclient.py` (หน้าเว็บเรียกบริการบอท)
ไฟล์คู่กัน: `docs/subsystem-guides/CALENDAR_GUIDE.md` (การทำงานของ Calendar), `docs/exam-prep/ADVISOR_PREP.md` (เตรียมตอบอาจารย์), `docs/exam-prep/FILE_GUIDE.md` (หน้าที่ทุกไฟล์)

ข้อความที่เป็น "ความรู้ทั่วไปของ Playwright" (ไม่ได้มาจากโค้ดของโปรเจกต์) ผมกำกับไว้ว่า "ทั่วไป"

## 0. สรุปสั้น (พูดได้ใน 30 วินาที)

บอทคือโปรแกรม Python ที่ใช้ไลบรารี Playwright สั่งเปิดเบราว์เซอร์ Chromium จริงๆ ขึ้นมาหนึ่งหน้าต่าง ใช้โปรไฟล์ที่ล็อกอินบัญชี Google ไว้แล้ว เข้าไปที่ลิงก์ห้อง Google Meet กดปุ่ม "ขอเข้าร่วม" รอผู้จัดประชุมกดอนุญาต แล้วกดเปิดคำบรรยายสด (CC) หลังจากนั้นฝังสคริปต์ JavaScript ลงในหน้า Meet เพื่อคอยอ่านข้อความคำบรรยายและรายชื่อคนในห้อง (จากแผง "บุคคล") ส่งกลับมาให้ Python ซึ่งเขียนลงฐานข้อมูล ระหว่างนั้นมีตัวเฝ้าระวังตรวจทุก 15 วินาทีว่าบอทยังอยู่ในห้อง

## 1. Playwright คืออะไร (ทั่วไป) และคำที่ใช้ในโค้ด

**Playwright (ทั่วไป):** ไลบรารีโอเพนซอร์สสำหรับสั่งเบราว์เซอร์ด้วยโปรแกรม (เปิดหน้า คลิก พิมพ์ อ่านข้อมูลในหน้า รันสคริปต์ในหน้า) เดิมใช้ทดสอบเว็บ แต่ใช้ทำบอทได้เช่นกัน รองรับ Chromium, Firefox, WebKit มี API ภาษา Python แบบ async (`async_playwright`) ตอนสั่ง Chromium ใช้โปรโตคอล Chrome DevTools Protocol (CDP) สื่อสารกับเบราว์เซอร์ และมีเบราว์เซอร์ Chromium ของตัวเองให้ติดตั้ง (`playwright install chromium`)

ในโปรเจกต์: README ให้ติดตั้งด้วย `venv\Scripts\python -m playwright install chromium` (`README.md` หัวข้อ "ติดตั้งและรัน") และ `requirements.txt` มี `playwright`

| คำ/ฟังก์ชันของ Playwright | ความหมาย (ทั่วไป) | ใช้ในโปรเจกต์ที่ไหน |
|---|---|---|
| `async_playwright()` | เริ่ม Playwright แบบ async (ต้องเรียกใน `async with`) | `bot/meet_engine.py:17` import, `:603` ใช้ใน `_run` |
| `pw.chromium.launch_persistent_context(user_data_dir=...)` | เปิด Chromium พร้อม "โปรไฟล์ถาวร" (เก็บคุกกี้ การล็อกอิน) ไว้ในโฟลเดอร์ ปิดแล้วเปิดใหม่ยังล็อกอินอยู่ | `:611-618` ใช้โฟลเดอร์ `.meet_profile` (`:19`) |
| `page` | แท็บหนึ่งแท็บของเบราว์เซอร์ | `:620` |
| `page.goto(url)` | ไปที่ URL | `:628`, `:646` |
| `page.get_by_role("button", name=...)` | หาปุ่มจากบทบาท (button) และชื่อ/ป้ายที่มองเห็นหรือ `aria-label` (รับ regex) | ปุ่มเข้าร่วม `:654`, ปุ่มคำบรรยาย `:384` |
| `locator(...)` | ตัวแทนของ "องค์ประกอบที่หาจากตัวเลือก (selector)" ใช้ตรวจ `count()`, `wait_for()`, `click()` | ปุ่มวางสาย `:671-674`, ปุ่มบุคคล `:475-477` |
| `page.evaluate(js)` | รัน JavaScript ในหน้า แล้วรับผลกลับมาเป็นข้อมูล Python | ติดตั้งตัวจับ `:468`, อ่านรายชื่อ `:472` |
| `page.expose_function(name, fn)` | ทำให้ JavaScript ในหน้าเรียกฟังก์ชัน Python ได้ (เป็นสะพานจากหน้า Meet กลับมา Python) | `:623-625` ชื่อ `__onCaption` |
| `page.keyboard.press(...)`, `page.mouse.move(...)` | จำลองการกดแป้นและขยับเมาส์ | ปิดไมค์/กล้อง `:650-651`, ขยับเมาส์ให้แถบปุ่มโผล่ `:410-411`, กด `c` เปิดคำบรรยาย `:417` |
| `context.new_cdp_session(page)` | ส่งคำสั่ง CDP ตรง (ระดับต่ำกว่า API ปกติ) | ย้าย/ย่อหน้าต่างเบราว์เซอร์ `:447-457` |
| `context.close()` | ปิดเบราว์เซอร์ | `:696` (ใน `finally`) |

**ทำไมเลือก Playwright แทนการอัดเสียงหรือปลั๊กอิน:** Meet ถอดเสียงเป็นคำบรรยายให้อยู่แล้ว บอทแค่ "อ่านจากหน้าจอ" (ตามที่ Proposal อธิบายไว้ในหัวข้อ Speech-to-Text) จึงไม่ต้องทำระบบถอดเสียงเอง ไม่ต้องเก็บไฟล์เสียง แลกกับการพึ่งโครงสร้างหน้าเว็บของ Meet ที่ Google เปลี่ยนได้ไม่แจ้ง

## 2. ภาพรวมการทำงานตั้งแต่กดปุ่มจนบอทอยู่ในห้อง

```

ui/tab_bot.py:12 _start                  bot_service.py:278 /bot/start               bot/meet_engine.py
  └─ botclient.start        ──HTTP──►     ├─ ตรวจสิทธิ์ผู้ใช้ (:284)                  MeetCaptionEngine

                                          ├─ เตรียมคิวเขียน DB (:305-306)               └─ _run (:601) ← Playwright ทำงานที่นี่
                                          └─ engine.start(meet_url) (:310)                  │ ส่ง event (_emit :341)
```

จุดสำคัญ: เอนจินรันเป็น `asyncio` task อยู่ในโปรเซสบริการบอท (`bot_service.py:310` `engine.start(...)` → `meet_engine.py:309` `asyncio.create_task(self._run(url))`) ไม่ได้ผูกกับหน้าเว็บ ดังนั้นหน้าเว็บรีโหลดหรือปิดแล้วบอทยังอยู่ในห้อง

## 4. การเปิดคำบรรยาย (CC) ตรวจจากหน้าจอจริง

โจทย์: การกดปุ่มคำบรรยายตอนยังอยู่ห้องรอไม่มีผล แต่ถ้าแค่ "กดแล้วรายงานว่าสำเร็จ" ระบบจะหลอกตัวเอง โค้ดจึง **ตรวจจากหน้าจอจริงทุกครั้ง**

| ฟังก์ชัน | หน้าที่ | บรรทัด |
|---|---|---|
| `_caption_state` | ดูสถานะ: `on` (เห็นกรอบคำบรรยาย `.a4cQT` ที่แสดงอยู่ หรือปุ่มคำบรรยายเป็นแบบ "ปิด…" / `aria-pressed=true`), `off` (มีปุ่มให้กดเปิด), `unknown` (ไม่เจอปุ่มเลย) ข้ามปุ่ม "ตั้งค่า" | `:372-399` |
| `_enable_captions` | พยายามเปิด 3 รอบ: ขยับเมาส์ให้แถบปุ่มโผล่ (Meet ซ่อนแถบเมื่อไม่ขยับเมาส์) กดปุ่ม ถ้าไม่เจอปุ่มในรอบที่ 2 ขึ้นไปลองกดแป้น `c` แล้ว **ตรวจซ้ำจากหน้าจอ** คืน True เฉพาะเมื่อยืนยันได้ | `:401-422` |

## 5. แผง "บุคคล": การเปิดและการอ่านรายชื่อ

**โจทย์:** คนที่เข้าห้องแต่ไม่พูด จะไม่มีข้อความคำบรรยายเลย ระบบจึงต้องอ่านรายชื่อจากแผง "บุคคล" (รายชื่อผู้เข้าร่วมของ Meet) เพื่อตั้งสถานะ "เข้าร่วม"

### 5.1 การเปิดแผง (กดปุ่มเองถ้ายังไม่เปิด)

โค้ดอยู่ที่ `_scan_participants` (`bot/meet_engine.py:470-490`) ลำดับ:
1. รัน JavaScript อ่านรายชื่อก่อน (`:472`) ถ้าได้ `panel: true` แปลว่าแผงเปิดอยู่ ใช้ผลได้เลย
2. ถ้า `panel` เป็นเท็จ และยังพยายามไม่ครบ 2 ครั้ง (`PEOPLE_OPEN_ATTEMPTS` `:274`) → **บอทหาปุ่ม "บุคคล" แล้วคลิกเปิดแผง** (`:473-481`)
   - ตัวเลือกหลักคือปุ่มที่มี `jsname="ocqpFe"` **และ** ข้อความตรง `PEOPLE_LABEL_RE` (`:264`: ขึ้นต้นด้วย บุคคล / ผู้คน / ผู้เข้าร่วม / People / Participants / Show everyone) `jsname="ocqpFe"` ใช้ร่วมกันหลายปุ่มในแถบเครื่องมือ จึงต้องกรองด้วยข้อความ ห้ามหยิบตัวแรก (คอมเมนต์ `:262-263`)
   - ถ้าไม่เจอ ใช้ตัวเลือกสำรอง `PEOPLE_BUTTON_FALLBACK` (`:265-268`: ปุ่มที่ `aria-label` ขึ้นต้นด้วยคำเหล่านั้น) ห้ามจับแบบ "มีคำว่า" เพราะจะไปโดนปุ่มอื่น เช่น ปุ่ม "การประชุมนี้เปิดให้ทุกคนเข้าร่วมได้"
   - คลิกแล้วรอ 1 วินาที แล้วอ่านใหม่ (`:479-481`)
3. อ่านได้ → ส่ง event `participants` พร้อมรายชื่อ (`:482-485`) ถ้าพยายามครบ 2 ครั้งแล้วยังไม่เจอแผง → ส่งสถานะเตือนครั้งเดียว พร้อมรายการที่บอทเห็นในหน้า เพื่อใช้ปรับ selector ตามหน้า Meet จริง (`:486-490`)

เหตุผลที่จำกัด 2 ครั้ง: ตามคอมเมนต์ที่ `:274` "ยอมแพ้ที่รอบคู่ = แผงกลับมาปิดเหมือนเดิม" คือถ้ากดสลับเปิด-ปิดแล้วไม่สำเร็จ จะไม่ทิ้งแผงเปิดค้างอยู่

### 5.2 การอ่านรายชื่อ (JavaScript ในหน้า Meet)

`JS_READ_PARTICIPANTS` (`:228-261`): หา `[role="list"]` ในหน้าที่ป้าย (`aria-label`) ตรงกับคำว่า participants/people/everyone/ผู้เข้าร่วม/ผู้คน/บุคคล ฯลฯ และไม่ใช่รายการ "รออนุญาตเข้าห้อง" (`:231-237`) แล้วอ่านทุก `[role="listitem"]` เอาชื่อจาก `aria-label` (ถ้าไม่มี ใช้ข้อความตัวแรกในรายการ) **ข้ามแถวที่มี "(คุณ)" หรือ "(You)"** ซึ่งเป็นแถวของบอทเอง (`:249`) ตัดชื่อซ้ำและชื่อที่ยาวเกิน 100 ตัวอักษร

- อ่านพลาดไม่กระทบการจับคำบรรยาย (กลืน exception ที่ `:578-579`)

### 5.4 หลังอ่านได้ ไปเกิดอะไรกับรายชื่อ

## 6. หน้าต่าง Chrome ของบอท: ซ่อน แสดง ย่อ (`_place_window`)

ค่าเริ่มต้น `BOT_WINDOW=hidden` (`:22`) บอทไม่ให้หน้าต่างเด้งรบกวนผู้ใช้ วิธีทำ (`:443-459`):
1. ตอนเปิดเบราว์เซอร์ ใส่ `--window-position=-2400,-2400` ให้หน้าต่างเกิดนอกจอ (`:607`)
2. `_place_window` ผ่าน CDP (`Browser.getWindowForTarget`, `Browser.setWindowBounds`): ตั้งเป็นหน้าต่างปกติ → ย้ายเข้าจอที่ตำแหน่ง (0,0) → ขยายเต็มจอ → **ย่อ (minimize)** ถ้าต้องซ่อน (`:450-456`)
3. ผู้ใช้คลิกที่ Taskbar เพื่อเปิดดูได้ หน้าต่างจะกลับมาเต็มจอ (คอมเมนต์ `:451`)
4. ถ้าต้องล็อกอิน Google (ขั้น 6 ข้างบน) แสดงหน้าต่างให้ผู้ใช้เห็นก่อน แล้วย่อกลับหลังล็อกอินเสร็จ (`:632-633`, `:644-645`)

เหตุที่ใช้ "ย่อ" ไม่ใช่ "ย้ายออกนอกจอ" ตามคอมเมนต์ `:444-445`: หน้าต่างนอกจอผู้ใช้เรียกกลับเองไม่ได้ และคอมเมนต์ `:20` ระบุว่าทดสอบแล้วว่าย่อไว้ Playwright ไม่หน่วงหน้า
ห้ามปิดหน้าต่างนี้: การปิดเบราว์เซอร์ทำให้บอทหลุดจากห้อง (watchdog จับได้ที่ `:516-518`, `:552-555`)

## 7. จาก "หน้า Meet" กลับมา "Python": สคริปต์ฝังและสะพาน

- **ฝังสคริปต์:** `_install_watcher` (`:461-468`) เรียก `page.evaluate(JS_CAPTION_WATCHER)` ก่อนนั้นตั้งตัวนับ id แถวให้ต่อจากรอบก่อนเสมอ (`SEQ_BASE_STEP` `:285`) เพราะถ้าหน้าโหลดใหม่ ตัวนับในหน้าจะรีเซ็ตและ id ชนกับของเดิม
- **สะพาน:** สคริปต์เรียก `window.__onCaption(payload)` (ฟังก์ชันที่ `expose_function` สร้างไว้ที่ `:623-625`) → Python เรียก `_emit(type="caption", ...)` (`:341`) → callback `on_event` ของบริการบอท (`bot_service.py:201`)
- **รายละเอียดตัวจับ:** `MutationObserver` เฝ้ากรอบคำบรรยาย, รวมข้อความด้วย "จุดยึด" (`mergeCommit` `:94-115`), ปิดแถวเมื่อเงียบ 1.5 วินาที (`FINALIZE_MS`), ล้างข้อมูลแถวที่จบแล้ว (`cleanup` `:130-136`) อ่านต่อใน `docs/exam-prep/ADVISOR_PREP.md` หัวข้อ 1.2

## 8. การเฝ้าระวัง (watchdog) ทุก 15 วินาที

`_monitor` (`:501`) ตรวจทุก `WATCHDOG_INTERVAL_S` = 15 วินาที (`:278`):

| ตรวจอะไร | ผลถ้าผิดปกติ | บรรทัด |
|---|---|---|
| หน้า/เบราว์เซอร์ปิดหรือ crash | หยุดบอท (`_EngineLost`) | `:516-518`, `:529-530` |
| ปุ่มวางสายหายติดกัน 3 รอบ (`LEFT_ROOM_STRIKES`) | ถือว่าประชุมจบหรือหลุดห้อง ปิดการบันทึก | `:540`, `:552-555` |
| สั่ง JavaScript ในหน้าไม่ได้ติดกัน 5 รอบ (`EVAL_FAIL_STRIKES`) | ถือว่าหน้าตาย | `:546-550` |
| ตัวจับคำบรรยายหาย (หน้าถูกโหลดใหม่) | เปิดคำบรรยายและติดตั้งตัวจับใหม่ | `:559-567` |
| ไม่เห็นกรอบคำบรรยายเกิน 60 วินาที | ลองเปิดคำบรรยายใหม่ | `:580-592` |
| ไม่มีคำบรรยายใหม่เกิน 300 วินาที | เตือนในสถานะ (อาจแค่ไม่มีใครพูด) | `:593-598` |
| ครบเวลาสูงสุดที่ตั้ง (ถ้ามี) | ออกจากห้อง | `:534-535` |

หมายเหตุ: ตรวจปุ่มวางสายด้วย `count()` ไม่ใช่ `is_visible()` เพราะแถบปุ่มของ Meet ซ่อนตัวเองเมื่อไม่ขยับเมาส์ แต่ปุ่มยังอยู่ใน DOM (คอมเมนต์ `:538-539`)

## 9. สิ่งที่ทดสอบแล้ว และข้อจำกัดที่ต้องบอกอาจารย์ตรงๆ

**เทสต์ที่พิสูจน์ส่วนนี้ (ใน `tests/` ทดสอบกับหน้า Meet "จำลอง" ใน Chromium จริง ไม่ใช่ห้อง Meet จริง):**
- `test_join_button.py` (3 ข้อ): ปุ่มเข้าห้อง รวมหน้า "เปลี่ยนที่นี่"
- `test_participant_scan.py` (8 ข้อ): อ่านรายชื่อ และจังหวะอ่าน (ทันทีที่เข้า ตอนหยุด)
- `test_caption_watcher.py` (4 ข้อ): ตัวจับคำบรรยาย sliding window และการแก้คำย้อนหลัง
- `tools/soak_sim.py lifecycle`: watchdog 5 กรณี (ไม่อยู่ใน `tests/`)

**กับ Meet จริง:** Proposal หัวข้อ "ทดสอบการอ่านรายชื่อผู้เข้าร่วมในห้อง Google Meet จริง" ระบุว่าทดสอบ 1 ห้อง 2 คนที่ไม่พูด บอทอ่านรายชื่อจากแผง "บุคคล" ได้ และภาพที่ 26–28 แสดงผล แต่ **ไม่มีบันทึกแยกว่าบอทกดเปิดแผงเองได้ในห้องจริง** (คอมเมนต์ `meet_engine.py:226` ยังเขียนว่ายังไม่ได้ทดสอบข้อนี้ ซึ่งเก่ากว่าผลทดสอบใน Proposal)

**ความเสี่ยงและข้อจำกัด:**
1. **พึ่งโครงสร้างหน้าเว็บของ Meet:** ตัวเลือกที่ใช้ (`.a4cQT` กรอบคำบรรยาย, `jsname`, ป้ายปุ่ม, `role="list"`) ไม่มีเอกสารรับรอง Google เปลี่ยนได้ไม่แจ้ง ถ้าพังต้องปรับ selector ที่ `meet_engine.py` เครื่องมือช่วยดูโครงสร้างใหม่คือ `tools/meet_people_probe.js`
2. **Google อาจไม่ยอมให้ล็อกอินในเบราว์เซอร์ที่ควบคุมด้วยโปรแกรม:** Proposal ข้อจำกัดข้อ (5) เล่าว่าพบข้อความว่าเบราว์เซอร์หรือแอปอาจไม่ปลอดภัย ระบบจึงอาศัยบัญชีที่ล็อกอินไว้ล่วงหน้าในโปรไฟล์ `.meet_profile` ของบอท หรือเข้าแบบไม่ล็อกอินกับห้องที่เปิดให้ทุกคนเข้าได้ (บอทใช้ Chromium ที่ Playwright ติดตั้งให้ ไม่ใช่ Chrome ที่เครื่องผู้ใช้ เพราะ `launch_persistent_context` ไม่ได้ระบุ `channel`)
3. **ปิดไมค์/กล้องด้วยการกดทางลัด (toggle) ไม่ใช่ตั้งค่าตรงๆ** (`:650-651`) จึงพึ่งสถานะเริ่มต้นของ Meet (นี่เป็นข้อสังเกตจากการอ่านโค้ด ผมไม่ได้ทดสอบกรณีที่เปิดไว้ก่อนแล้ว) ภาพที่ 23, 26 ของ Proposal แสดงบอทปิดไมค์ในห้องจริง
4. **ทีละห้องต่อเครื่อง** (บอทตัวเดียว `bot_service.py:287-290`)
5. **บอทเป็นผู้เข้าร่วมที่เห็นในห้อง** (ชื่อ "Meet Sync") ผู้จัดต้องกดอนุญาต ซึ่งเป็นการออกแบบที่ตั้งใจ (TOR ระบุให้ผู้จัดยอมรับบอทเอง)
6. **เกินความรู้ที่ผมตรวจ:** ผมไม่ได้ตรวจเอกสารของ Playwright ว่า Chromium รุ่นที่ติดตั้งส่งแฟล็ก `--no-sandbox` ให้เองหรือไม่ (แถบเตือนของ Chrome ที่เห็นในภาพที่ 11 บอกว่าใช้แฟล็กนี้ แต่โค้ดของโปรเจกต์ไม่ได้ใส่เอง)

## 11. ถ้าอาจารย์ถาม

| คำถาม | คำตอบ |
|---|---|
| Playwright คืออะไร ทำไมไม่ใช้ API ของ Meet | Playwright สั่งเบราว์เซอร์จริงด้วยโปรแกรม Meet ไม่มี API ทางการสำหรับอ่านคำบรรยายแบบเรียลไทม์ให้บอท จึงอ่านจากหน้าจอ (ผมไม่ได้ตรวจเอกสาร Google ว่ามี API ทางการหรือไม่ ข้อนี้เป็นเหตุผลที่โครงงานอธิบายไว้ใน Proposal) |
