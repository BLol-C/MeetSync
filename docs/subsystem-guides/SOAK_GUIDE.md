# คู่มือ soak test: คืออะไร ทำไมต้องมี และทำงานอย่างไร

เอกสารนี้อธิบายชุดเครื่องมือ "soak" (ทดสอบให้ระบบรันต่อเนื่องนานๆ) ที่อยู่ใน `tools/` ว่าแต่ละตัววัดอะไร พิสูจน์อะไรได้ และพิสูจน์อะไรไม่ได้
ข้อมูลตัวเลขมาจากไฟล์ CSV เดิมของวันที่ 12 และ 13 ต.ค. 2569 (ที่กู้คืนจากถังขยะ) และจากการรันจำลองของวันที่ 11 พ.ย. 2569
ที่ผมไม่ได้ตรวจเองจะเขียนกำกับไว้ว่า "ผมไม่ได้ตรวจ" หรือ "ยืนยันไม่ได้"

ไฟล์ที่เกี่ยวข้อง: `docs/exam-prep/FILE_GUIDE.md` (หัวข้อ `tools/`) และ `docs/exam-prep/TOR_MAP.md` (ฟังก์ชัน 1)

## 1. soak test คืออะไร และทำไมต้องมี

**คำว่า soak** คือการปล่อยให้ระบบทำงานต่อเนื่องเป็นเวลานาน แล้วดูว่าสภาพของมันเสื่อมลงหรือไม่ (หน่วยความจำเพิ่มเรื่อยๆ ข้อความหาย ข้อความซ้ำ บอทหลุด) ต่างจากการทดสอบสั้นๆ ที่ปัญหาเหล่านี้ยังไม่ปรากฏ

**ทำไมโครงงานนี้ต้องมี**
1. **เป็นข้อกำหนดของโครงงาน** วัตถุประสงค์ข้อ 3 และขอบเขตข้อ 1 ใน Proposal เขียนว่า "บอททำงานต่อเนื่องในห้องประชุมได้อย่างเสถียรอย่างน้อย 1 ชั่วโมง โดยไม่เกิดหน่วยความจำรั่วไหล โดยมีการทดสอบเสถียรภาพของบอทเป็นหลักฐาน" ดังนั้นต้องมีตัวเลขที่เอาไปแสดงอาจารย์ได้
2. **บอทต้องอยู่ในห้องนาน** ประชุมจริงยาวเป็นชั่วโมง บอทเปิด Chrome ค้างไว้และมีสคริปต์ฝังในหน้า Meet ทำงานตลอด ถ้ามีจุดที่เก็บข้อมูลสะสมโดยไม่คืน หน่วยความจำจะโตจนเครื่องช้าหรือ Chrome ค้าง ปัญหานี้เห็นไม่ได้ในการทดสอบ 5 นาที
3. **ต้องไม่ทำให้ข้อมูลหาย** ถ้าบอทหลุดกลางคันหรือตัวจับคำบรรยายหยุด ข้อความที่ควรบันทึกจะขาด ต้องมีกลไกเฝ้าระวัง (watchdog) และต้องทดสอบว่ากลไกนั้นทำงาน

**ตัวอย่างจุดที่เสี่ยงรั่วในระบบนี้**
- ในหน้า Meet: ตัวจับคำบรรยายเก็บข้อมูลต่อแถวไว้ในโครงสร้าง `Map` และตัวจับเวลา (`bot/meet_engine.py:40-43` `lastRaw`, `commit`, `lastEmitAt`, `timers`) ถ้าไม่ลบเมื่อแถวจบ ก็จะโตไปเรื่อยๆ
- ใน Chrome: หน้า Meet เองสร้าง DOM คำบรรยายใหม่ตลอด
- ใน Python: คิวเขียนข้อความลง MySQL และกล่องคำบรรยายสดที่เก็บแถวไว้ให้หน้าเว็บอ่าน (`bot_service.py:46` จำกัดไว้ที่ 150 แถวตามค่าเริ่มต้น)

## 3. เครื่องมือสี่ตัวและสิ่งที่แต่ละตัวพิสูจน์ได้

| เครื่องมือ | วัด/ตรวจอะไร | ใช้ Meet จริงไหม | พิสูจน์ได้ | พิสูจน์ไม่ได้ |
|---|---|---|---|---|
| `tools/proc_monitor.ps1` | หน่วยความจำของโปรเซส `python` และ `chrome`/`chromium` ทุก N วินาที เก็บเป็น CSV | **ใช่** ต้องรันขนานกับการประชุมจริง | หน่วยความจำของเครื่องตอนบอทอยู่ในห้องจริงโตไหม | ว่าส่วนไหนโต (วัดรวมทั้งเครื่อง ดูข้อ 6) |
| `tools/stability_check.py` | เทียบ "บทพูด" 90 ประโยคกับ transcript ที่บันทึกใน DB: จับได้กี่ %, ประโยคหาย, ช่วงเวลา, ช่วงซ้ำ | **ใช่** ต้องมีคนอ่านบทตามจริง | บอทจับข้อความได้ครบตลอดชั่วโมงไหม | ความถูกต้องของคำบรรยายของ Google เอง |
| `tools/soak_sim.py soak` | หน้า Meet ปลอมใน Chromium: เทียบข้อความที่จับได้กับที่ "พูดจริง" ทุกคำ และวัด JS heap, DOM node, event listener ผ่าน Chrome DevTools | **ไม่** (จำลอง) | ตรรกะของตัวจับคำบรรยายถูกต้องและไม่สะสมข้อมูลในหน้า | พฤติกรรมของ Meet จริง |
| `tools/soak_sim.py lifecycle` | ทดสอบ watchdog 5 สถานการณ์ในหน้าปลอม | **ไม่** (จำลอง) | watchdog ตอบสนองถูกเมื่อประชุมจบ หน้าปิด โหลดใหม่ ครบเวลา | ว่า Meet จริงเกิดเหตุเหล่านี้แบบเดียวกัน |

README ของโปรเจกต์ระบุไว้เองว่า "ตัวจำลองพิสูจน์ได้แค่ตรรกะ ไม่ใช่ Meet จริง" จึงต้องมีการวัดกับห้องจริงด้วย `proc_monitor.ps1`

## 4. แต่ละตัวทำงานอย่างไร

### 4.1 `proc_monitor.ps1` (วัดกับห้องจริง)

ทุก `IntervalSeconds` วินาที (ค่าเริ่มต้น 60) สคริปต์ทำ:
1. `Get-Process python` รวมค่า `WorkingSet64` (หน่วยความจำจริงที่โปรเซสใช้อยู่) ของโปรเซสชื่อ python ทั้งหมด
2. `Get-Process chrome, chromium` รวม `WorkingSet64` ของโปรเซสชื่อ chrome/chromium ทั้งหมด (รวมโปรเซสลูก GPU/renderer) และนับจำนวนโปรเซส
3. เขียนหนึ่งบรรทัดลงไฟล์ `soak_<วันที่-เวลา>.csv` คอลัมน์ `time, python_mb, chrome_mb, chrome_procs, total_mb` (`total_mb` = python + chrome)

รันจนครบ `-Minutes` หรือกด Ctrl+C

**สรุปผล** `-Summarize <ไฟล์>`: แบ่งข้อมูลเป็นสี่ส่วนเท่าๆ กัน เอาค่าเฉลี่ย `total_mb` ของส่วนแรกเทียบกับส่วนสุดท้าย ถ้าช่วงท้ายสูงกว่าช่วงต้นไม่เกิน 15% ถือว่า "ผ่าน (ไม่พบแนวโน้มรั่ว)" ถ้าเกินขึ้น "น่าสงสัย" (ต้องมีอย่างน้อย 8 แถว)

### 4.2 `stability_check.py` (ตรวจว่าจับข้อความครบ)

- `make` สร้างบทพูด 90 ประโยค (`tools/stability_script.txt`) ทุกประโยคไม่ซ้ำกันและมีเลขกำกับ ผู้พูด 2 คนสลับกันอ่านทีละบรรทัดทุก ~40 วินาที รวมประมาณ 60 นาที
- `check <meeting_id>` อ่านบทและ transcript ใน DB เทียบความคล้ายแบบไม่สนช่องว่าง (เผื่อ CC ถอดคำผิดเล็กน้อย) รายงาน: ประโยคที่จับได้กี่ %, ประโยคที่หายไป, จำนวนช่วงที่บันทึกในแต่ละช่วงเวลา และช่วงที่ข้อความซ้ำกันเป๊ะ

### 4.3 `soak_sim.py soak --minutes N` (จำลองในหน้าปลอม)

1. เปิด Chromium แบบไม่มีหน้าจอ โหลดหน้า Meet ปลอมที่มี "คนพูด" ต่อเนื่อง สุ่มชื่อ สุ่มความยาวประโยค ตัดหัวข้อความแบบ sliding window และสร้างกรอบคำบรรยายใหม่เป็นระยะ (ทุก 45 วินาที) เหมือนที่ Meet ทำ
2. ฝังตัวจับคำบรรยายจริง (`JS_CAPTION_WATCHER`) ลงหน้าปลอมนั้น
3. ทุก 15 วินาที สั่งเก็บขยะ (garbage collection) แล้ววัด `JSHeapUsedSize`, `Nodes`, `JSEventListeners` ผ่าน Chrome DevTools
4. หน้าปลอมเก็บ "เฉลย" ว่าแต่ละประโยคพูดว่าอะไร เมื่อจบเทียบข้อความ final ที่ตัวจับส่งมากับเฉลย นับประโยคที่ไม่มี event เลย และข้อความไม่ตรง
5. หน่วยความจำ: เทียบค่าเฉลี่ยหนึ่งในสี่แรกกับหนึ่งในสี่สุดท้าย ผ่านเมื่อ **JS heap โตน้อยกว่า 3 MB และ DOM node เพิ่มน้อยกว่า 200 และ listener เพิ่มน้อยกว่า 50** รวมกับ ข้อความครบและไม่ผิดเลย

### 4.4 `soak_sim.py lifecycle`

ย่นเวลา watchdog ให้สั้น แล้วทดสอบ 5 สถานการณ์บนหน้าปลอม: ปกติ (ต้องไม่หยุดเอง), ประชุมจบ (ปุ่มวางสายหาย), หน้าถูกปิด, reload (ต้องติดตั้งตัวจับใหม่และนับ id ต่อ), ครบเวลาสูงสุด

## 5. ผลที่มีอยู่ตอนนี้

**ข้อมูลเดิมกับห้องจริง** (คำนวณซ้ำจาก CSV เอง ใช้เกณฑ์ของ `proc_monitor.ps1`)

| | รอบ 12 ต.ค. (66 ตัวอย่าง ~65 นาที) | รอบ 13 ต.ค. (63 ตัวอย่าง ~62 นาที) |
|---|---|---|
| รวม ช่วงแรก → ช่วงท้าย | 1,399 → 1,015 MB (ลด 27.5%) | 1,241 → 1,015 MB (ลด 18.2%) |
| ค่าสูงสุด | 1,670 MB | 1,470 MB |
| Python | พุ่งสูงสุด 567 MB ใน 14 นาทีแรก แล้วนิ่ง 273–281 MB | ฐาน 190–280 MB (มัธยฐาน 222) พุ่งเป็นระยะถึง 595 MB |
| Chrome | ลดจาก 1,266 MB เหลือราว 700 MB | ลดเหลือราว 660 MB ที่นาทีที่ 25 แล้วไต่เป็นราว 790 MB ตอนท้าย (+15% ใน 38 นาที) |
| ผลตามเกณฑ์ | ผ่าน | ผ่าน แต่ดูข้อ 6 |

**จำลอง 10 นาที** (รันวันที่ 11 พ.ย. 2569): พูด 123 ประโยค จับครบ ไม่ผิดเลย JS heap 0.8 → 0.9 MB, DOM node 21 → 20, listener 0 → 0 ผ่าน (ตัวเลขใน Proposal หน้า 67 คือรอบเดิม 150 ประโยค จำนวนประโยคแต่ละรอบไม่เท่ากัน)

**เทสต์ที่เกี่ยวข้องใน `tests/`**: `test_caption_watcher.py` (4 ข้อ ตัวจับกับหน้าจำลองใน Chromium จริง), `test_stability_check.py` (5 ข้อ เครื่องมือเทียบบทกับ transcript) ผ่านทั้งหมดในการรันวันที่ 11 พ.ย.

## 6. ข้อจำกัดของวิธีวัด (ควรรู้ก่อนอ้างผลกับอาจารย์)

1. **วัดรวมทั้งเครื่อง ไม่ใช่เฉพาะบอท** `proc_monitor.ps1` รวมทุกโปรเซสที่ชื่อ `python` (รวม Streamlit, บริการบอท uvicorn และ python อื่นที่รันอยู่ เช่นเทสต์หรือเครื่องมืออื่น) และทุกโปรเซสชื่อ `chrome`/`chromium` (ถ้าเปิด Chrome ส่วนตัวไว้ก็นับรวมด้วย) ในไฟล์เดิม `chrome_procs` เป็น 9 ในแทบทุกตัวอย่าง (ยกเว้นตัวอย่างแรกของรอบ 12 ต.ค. ที่เป็น 0 เพราะบอทยังไม่เปิด Chrome) น่าจะมีแต่ของบอท แต่ผมยืนยันไม่ได้ ที่ Proposal อธิบายว่า Python พุ่งเพราะมีโปรแกรมอื่นรันบนเครื่องเดียวกัน จึงสอดคล้องกับวิธีวัดนี้ (ผมไม่ได้ตรวจสาเหตุจริงของแต่ละจุดที่พุ่ง)
2. **`WorkingSet64` ไม่ใช่ตัวชี้ "การรั่ว" โดยตรง** เป็นหน่วยความจำจริงที่โปรเซสถืออยู่ซึ่งระบบปฏิบัติการปรับขึ้นลงได้เอง ค่าโตอาจเป็น cache ปกติ ค่าไม่โตก็ไม่ได้ยืนยันว่าไม่มีการรั่วเล็กๆ
3. **เกณฑ์ "เฉลี่ย 1/4 แรก เทียบ 1/4 สุดท้าย" มองไม่เห็นการไต่ช้าๆ ช่วงท้าย** ช่วงต้นการประชุมมีค่าสูงจากการเปิดหน้า Meet จึงทำให้ค่าเฉลี่ยช่วงแรกสูงเกินจริง ผ่านเกณฑ์ได้ง่ายแม้ช่วงท้ายกำลังไต่ขึ้น กรณีนี้เกิดจริงในรอบ 13 ต.ค.: รวมลด 18.2% (ผ่าน) แต่ Chrome ไต่จาก ~660 เป็น ~790 MB ตั้งแต่นาทีที่ 25 (+15%, ราว 2.2 MB ต่อนาที) ซึ่งเกณฑ์นี้ไม่เตือน
4. **ยาวแค่ ~1 ชั่วโมง ทดสอบ 2 รอบ** สรุปเรื่องการใช้งานนานกว่านี้ไม่ได้ (Proposal เขียนข้อจำกัดนี้ไว้แล้ว)
5. **ตัวจำลองพิสูจน์แค่ตรรกะของตัวจับ** ไม่แทนห้อง Meet จริง และไม่ได้วัดหน่วยความจำของ Python หรือ Chrome ตัวจริง (วัดเฉพาะ JS heap ในหน้าปลอม)
6. **ผู้เข้าร่วมและความถี่การพูดมีผล** รอบ 12 ต.ค. คนแทบไม่พูด รอบ 13 ต.ค. พูดต่อเนื่อง CSV ไม่เก็บจำนวนผู้พูดหรือจำนวนข้อความ จึงเทียบกับปริมาณงานของแต่ละรอบไม่ได้

**ถ้าจะวัดให้เชื่อถือขึ้น** (ยังไม่ได้ทำ ต้องให้คุณสั่ง ไม่ต้องแก้ระบบ): ปิดโปรแกรมอื่นและ Chrome ส่วนตัวก่อนวัด, ดูกราฟ `total_mb` และ `chrome_mb` ด้วยตา, และอ่านแนวโน้มเฉพาะหลังช่วงอุ่นเครื่อง (เช่นหลังนาทีที่ 25–30) ผมช่วยคำนวณความชันของ CSV ให้ได้ แต่ไม่ได้เปลี่ยนสคริปต์ `proc_monitor.ps1`

## 7. ขั้นตอนรัน (สรุปสั้น)

| ต้องการ | คำสั่ง (ที่โฟลเดอร์โปรเจกต์) |
|---|---|
| วัดกับห้อง Meet จริง ตลอดประชุม | เปิด `.\run` เริ่มบอทจากแท็บ ② แล้วในอีก PowerShell: `powershell -ExecutionPolicy Bypass -File tools\proc_monitor.ps1 -Minutes 70` |
| สรุปผล CSV | `powershell -File tools\proc_monitor.ps1 -Summarize soak_<เวลา>.csv` |
| สร้างบทพูด 90 ประโยค | `venv\Scripts\python tools\stability_check.py make` |
| เทียบบทกับ transcript | `venv\Scripts\python tools\stability_check.py check <meeting_id>` |
| จำลองตัวจับคำบรรยาย | `venv\Scripts\python tools\soak_sim.py soak --minutes 10` |
| ทดสอบ watchdog | `venv\Scripts\python tools\soak_sim.py lifecycle` |

ข้อควรระวังระหว่างวัดจริง: ห้ามปิดหน้าต่าง Chrome ของบอท (ย่อได้) เครื่องต้องไม่หลับ และไฟล์ `soak_*.csv` ไม่ขึ้น git (อยู่ใน `.gitignore`)
ข้อมูลประชุมจริงอยู่ใน DB ที่ใช้ `stability_check.py check` อ่าน จึงอย่าส่งผลที่มีข้อความประชุมจริงให้คนนอกโดยไม่ตรวจก่อน

## 8. ถ้าอาจารย์ถาม

| คำถาม | คำตอบที่ตรงกับข้อมูลที่มี |
|---|---|
| ทำไมต้องวัด 1 ชั่วโมง | เป็นข้อกำหนดของโครงงาน (วัตถุประสงค์ข้อ 3) และประชุมจริงยาวระดับนี้ ปัญหาสะสมเห็นได้ยากในการทดสอบสั้น |
| มีหลักฐานว่าไม่รั่วไหม | วัดกับ Meet จริง 2 รอบ (~65 และ ~62 นาที) หน่วยความจำรวมช่วงท้ายต่ำกว่าช่วงต้นทั้งสองรอบ แต่ Chrome รอบที่สองไต่ขึ้นช้าๆ ในครึ่งหลัง จึงยังสรุประยะยาวไม่ได้ และจำลองในหน้าปลอมไม่พบการสะสมใน JS heap/DOM/listener |
| วัดอะไร | หน่วยความจำจริงของโปรเซส python และ chrome รวมทั้งเครื่องทุก 1 นาที (ไม่แยกเฉพาะบอท) |
| ตัวจำลองใช้แทนของจริงได้ไหม | ไม่ได้ ใช้พิสูจน์ตรรกะตัวจับและ watchdog เท่านั้น |
| ถ้าบอทหลุดจะเกิดอะไร | watchdog ตรวจทุก 15 วินาที ถ้าหลุดห้องจะปิดการบันทึกอย่างเรียบร้อย ข้อความที่บันทึกแล้วไม่หาย (ทดสอบในหน้าจำลองด้วย `lifecycle`) |
