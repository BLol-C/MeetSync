## B. ข้อความที่ต้องแก้

### B1. หน้า 7 — เติมต่อท้ายย่อหน้า Playwright (ก่อนย่อหน้า Google Calendar API)

**แก้เป็น (เพิ่มย่อหน้าใหม่):**

จากการทดลองใช้งานกับ Google Meet จริง ทีมพบและแก้ปัญหาด้านความน่าเชื่อถือของบอท 4 เรื่อง ดังนี้ (1) บอทกดเปิดคำบรรยายตั้งแต่ยังอยู่ในห้องรอ ทั้งที่ผู้จัดประชุมยังไม่กดอนุญาต ปุ่มคำบรรยายยังไม่ปรากฏ การกดจึงไม่มีผล แต่ระบบกลับรายงานว่าเปิดสำเร็จ ทีมจึงเปลี่ยนให้ระบบ "ตรวจยืนยันจากหน้าจอ" ก่อนรายงานเสมอ (เห็นกรอบคำบรรยายหรือปุ่มเปลี่ยนเป็น "ปิดคำบรรยาย") และวนลองใหม่จนกว่าผู้จัดจะอนุญาต โดยรอได้สูงสุด 20 นาที (2) เมื่อผู้พูดพูดยาวต่อเนื่อง Google Meet จะตัดข้อความหน้า ๆ ของแถวคำบรรยายทิ้ง (sliding window) และแก้คำที่เคยแสดงไปแล้วย้อนหลัง วิธีเดิมที่ต่อข้อความใหม่เข้ากับข้อความสะสมโดยเดาว่าขึ้นต้นเหมือนเดิมทำให้ข้อความท่อนต้นถูกต่อซ้ำจนแถวเดียวบวมซ้ำ ทีมจึงเปลี่ยนเป็นหาจุดทับซ้อนระหว่างข้อความใหม่กับข้อความสะสมด้วย "จุดยึด" (ข้อความสั้น ๆ ที่ตรงกันพอดี) แล้วให้ข้อความล่าสุดทับตั้งแต่จุดนั้น พร้อมเขียนชุดทดสอบอัตโนมัติที่จำลองการตัดและแก้ข้อความของ Meet ใน Chromium จริง (3) คนที่พูดต่อเนื่องไม่หยุดทำให้ข้อความในแถวเดียวยาวเกินขนาดคอลัมน์ text ของ MySQL ระบบจึงแบ่งเป็นหลายช่วง (segment) เมื่อยาวเกิน 3,000 ตัวอักษร โดยลำดับ sequence_no ต่อเนื่องและข้อความรวมกันเท่าเดิม (4) หน้าต่าง Chrome ของบอทเด้งขึ้นมารบกวนผู้ใช้ทุกครั้ง ระบบจึงเปิดแล้วย่อหน้าต่างเก็บไว้ที่ Taskbar (ทดสอบแล้วว่า Chrome ไม่หน่วงหน้าที่ถูกย่อเมื่อควบคุมผ่าน Playwright) ผู้ใช้คลิกเพื่อเปิดดูได้ตลอด และหน้าต่างจะแสดงขึ้นเองเมื่อต้องล็อกอิน Google

### B4. หน้า 16 — ตาราง Process (เป็น 8 Process)

| Process | ชื่อ | ข้อมูลเข้า → แฟ้มข้อมูล → ข้อมูลออก |
|---|---|---|
| 1 | เข้าสู่ระบบ | email, id_token → users → สถานะเข้าสู่ระบบ |
| 2 | จัดการการประชุมและบทบาท | meet_url, หัวข้อ, หน่วยงาน, ครั้งที่, สถานที่, รายชื่อ+บทบาท+สถานะ+สาเหตุที่ไม่มา → meetings, speakers → คำสั่งเริ่มบอท |
| 3 | ดักจับและจัดเก็บข้อความ | timestamp, speaker, text จากบอท → speakers, transcript_segments |
| 4 **(ใหม่)** | ตรวจทานและยืนยัน transcript | การแก้ข้อความ/ผู้พูด/ลบ/รวมชื่อ จาก Host → transcript_segments (เก็บ original_text), speakers, meetings.status → transcript ที่ยืนยันแล้ว |
| 5 | ร่างรายงานด้วย AI | transcript + รายชื่อ/บทบาท → Gemini → summaries, agenda_items, action_items (ฉบับร่าง + คำเตือนจากการตรวจสอบ) |
| 6 **(ใหม่)** | ตรวจ แก้ไข และอนุมัติรายงาน | การแก้ไขรายงาน, คำสั่งอนุมัติ จากผู้มีสิทธิ์ → summaries (approved_by, approved_at), agenda_items, action_items, meetings.status |
| 7 | ส่งออก PDF และ Calendar | คำสั่งส่งออก → อ่านรายงานที่อนุมัติ → สร้าง PDF / Google Calendar API → อัปเดต action_items (calendar_synced, google_calendar_event_id) |
| 8 | เรียกดูประวัติย้อนหลัง | user_id → meetings, speakers, transcript_segments, summaries, agenda_items, action_items → ประวัติฉบับสมบูรณ์ |

### B5. หน้า 17–22 — Context Diagram, DFD และคำอธิบาย

**ต้องวาดภาพใหม่:** Context Diagram (ภาพที่ 2) เพิ่ม "ไฟล์ PDF รายงาน" เป็นข้อมูลออกถึง User/Host · Process 2 (ภาพที่ 4) เพิ่มรายชื่อ+บทบาท+สาเหตุที่ไม่มา · Process 4 ใหม่ (ตรวจทาน transcript) · Process 5 เดิมภาพที่ 6 (AI) เพิ่มรายชื่อ/บทบาทเป็นข้อมูลเข้าและ agenda_items เป็นแฟ้มข้อมูลออก · Process 6 ใหม่ (อนุมัติ) · Process 7 (ส่งออก) ข้อมูลเข้าเป็นรายงานที่อนุมัติแล้ว · Process 8 (ประวัติ) · และเปลี่ยนเลข Process ตามตารางข้อ B4

**คำอธิบายใต้ภาพ (แก้เป็น / เพิ่ม):**

**Process 2: จัดการการประชุมและบทบาท** — จากภาพที่ 4 Host ส่ง meet_url หัวข้อ หน่วยงาน ครั้งที่ สถานที่ และรายชื่อผู้เข้าร่วมพร้อมบทบาท (ประธาน เลขา กรรมการ/สมาชิก ผู้เข้าร่วมที่ไม่ใช่กรรมการ) สถานะการเข้าร่วม และสาเหตุที่ไม่มา เข้ากระบวนการที่ 2 ระบบบันทึกลงแฟ้ม meetings table และ speakers table พร้อมส่งคำสั่งเริ่มบอทพร้อม meet_url และ meeting_id ไปยังระบบบอทเข้าร่วมประชุม

**Process 3: ดักจับและจัดเก็บข้อความบทสนทนา** — จากภาพที่ 5 ระบบบอทส่ง timestamp, speaker, text เข้ากระบวนการที่ 3 โดยอ่าน meeting_id จากแฟ้ม meetings table จับคู่ชื่อผู้พูดกับรายชื่อใน speakers table (ชื่อที่ไม่ตรงถูกเพิ่มเป็นรายชื่อใหม่ที่มาจาก Meet) แล้วบันทึกลงแฟ้ม transcript_segments table พร้อม sequence_no ทุกประโยคที่จบ ข้อความยาวเกินเกณฑ์ถูกแบ่งเป็นหลายช่วงอัตโนมัติ

**Process 4 (ใหม่): ตรวจทานและยืนยัน transcript** — Host แก้ข้อความ เปลี่ยนผู้พูด ลบช่วงที่ไม่เกี่ยวข้อง หรือรวมชื่อที่ Meet แสดงเข้ากับรายชื่อที่ลงทะเบียน ระบบอ่านและปรับปรุงแฟ้ม transcript_segments table (เก็บ original_text เดิมไว้) และ speakers table เมื่อ Host กดยืนยัน ระบบเปลี่ยน meetings.status เป็น transcript_verified ซึ่งเป็นเงื่อนไขให้ AI ร่างรายงานได้

**Process 5: ร่างรายงานด้วย AI** — อ่าน transcript ที่ยืนยันแล้วจาก transcript_segments table และรายชื่อ/บทบาทจาก speakers table ส่ง prompt ให้ Gemini AI (แบ่งเป็นช่วงถ้าประชุมยาว) เมื่อได้ผลลัพธ์ JSON กลับมา ระบบตรวจว่ามติและภาระงานมีข้อความอ้างอิงอยู่ใน transcript จริง แล้วบันทึกฉบับร่างลง summaries table, agenda_items table และ action_items table พร้อมคำเตือนที่ตรวจพบ

**Process 6 (ใหม่): ตรวจ แก้ไข และอนุมัติรายงาน** — ประธาน เลขา หรือเจ้าของการประชุมตรวจคำเตือน แก้ไขวาระ มติ ภาระงาน แล้วกดอนุมัติ ระบบบันทึกผู้อนุมัติและเวลาลง summaries table (approved_by, approved_at) และเปลี่ยนสถานะเป็น approved รายงานที่อนุมัติแล้วถูกล็อก ยกเลิกอนุมัติเพื่อแก้ไขได้

**Process 7: ส่งออก PDF และ Google Calendar** — จากรายงานที่อนุมัติแล้ว ระบบสร้างไฟล์ PDF ตามแบบฟอร์มส่งให้ผู้ใช้ และส่งภาระงานที่มีวันกำหนด (summary, description, start_time, end_time) ไปยัง Google Calendar API เมื่อได้รับ google_calendar_event_id กลับมา ระบบอัปเดต calendar_synced และรหัสกิจกรรมที่แฟ้ม action_items table

**Process 8: เรียกดูประวัติการประชุมย้อนหลัง** — (ข้อความเดิม ปรับให้ดึงเพิ่มจาก speakers, transcript_segments, agenda_items ด้วย)

### B6. หน้า 23–24 — RDM

วาด RDM ใหม่เป็น **7 ตาราง** (เพิ่ม agenda_items) ด้วยคอลัมน์ต่อไปนี้ (ตัวหนา = ใหม่)

- **Users:** user_id (PK), google_sub, email, name, picture, **calendar_token**, created_at, last_login_at
- **Meetings:** meeting_id (PK), **owner_user_id (FK→Users)**, meet_url, title, **venue, meeting_no, org_name, scheduled_at**, started_at, ended_at, status
- **Speakers:** speaker_id (PK), meeting_id (FK), display_name, **meet_alias, email, role, attendance, absence_reason, source**
- **Transcript_Segments:** segment_id (PK), meeting_id (FK), speaker_id (FK), sequence_no, text, **original_text, edited_at, deleted**, spoken_at
- **Summaries:** summary_id (PK), meeting_id (FK, **UNIQUE** = 1:1), executive_summary, **other_matters, ai_snapshot**, model_used, **prompt_version**, generated_at, **edited_at, approved_by (FK→Users), approved_at**
- **Agenda_Items (ใหม่):** agenda_item_id (PK), summary_id (FK→Summaries), order_no, title, discussion, resolution, evidence
- **Action_Items:** action_item_id (PK), summary_id (FK), description, assignee, due_date, due_time, due_time_end, **evidence**, calendar_synced, google_calendar_event_id

ความสัมพันธ์: Users 1—N Meetings (owner_user_id) · Meetings 1—N Speakers · Meetings 1—N Transcript_Segments · Speakers 1—N Transcript_Segments · **Meetings 1—1 Summaries** · Summaries 1—N Agenda_Items · Summaries 1—N Action_Items · Users 1—N Summaries (approved_by)

### B7. หน้า 25–27 — คำอธิบายตาราง (แก้เป็น / เพิ่มคอลัมน์)

**ตาราง Users** เพิ่ม: `calendar_token` — โทเคนเชื่อมต่อ Google Calendar ของผู้ใช้คนนั้น (JSON) ใช้สร้างนัดหมายในปฏิทินของเจ้าของโทเคนเอง เก็บแยกจากการล็อกอินเพราะขอสิทธิ์ Calendar ต่างหาก

**ตาราง Meetings** — *ที่มา (แก้เป็น):* สร้างขึ้นเมื่อเจ้าของการประชุมกรอกข้อมูลการประชุมและรายชื่อผู้เข้าร่วมที่หน้าเว็บ (สถานะ scheduled) และเปลี่ยนสถานะตามขั้นตอนจนถึงอนุมัติ
เพิ่ม: `owner_user_id` เจ้าของการประชุม ใช้ตรวจสิทธิ์ · `venue` สถานที่ประชุม · `meeting_no` ครั้งที่ · `org_name` ชื่อหน่วยงาน (ทั้งสามใช้เป็นส่วนหัวรายงาน) · `scheduled_at` เวลานัดหมาย
**แก้ `title`:** ชื่อเรื่องการประชุม ผู้ใช้กรอกที่หน้าสร้างการประชุม (ตัดข้อความ "ยังไม่เชื่อมกับหน้าจอ" ออก)
**แก้ `status`:** ขั้นตอนทำงานของการประชุม scheduled → recording → transcript_review → transcript_verified → draft → approved ใช้ควบคุมว่าขั้นตอนใดทำได้ เช่น ต้องยืนยัน transcript ก่อน AI จึงจะร่างรายงานได้ (เดิม in_progress/completed)

**ตาราง Speakers** — *ที่มา (แก้เป็น):* รายชื่อที่เจ้าของการประชุมลงทะเบียนล่วงหน้าพร้อมบทบาท และชื่อผู้พูดที่ตรวจพบจาก Closed Captions แต่ไม่อยู่ในรายชื่อ (ที่มา = meet) ซึ่งเจ้าของอาจรวมเข้ากับชื่อที่ลงทะเบียนไว้ภายหลัง
เพิ่ม: `meet_alias` ชื่อที่ Google Meet แสดง (ถ้าต่างจากชื่อในรายงาน) ใช้จับคู่อัตโนมัติ · `email` ใช้ให้ประธาน/เลขาล็อกอินด้วยบัญชี Google เข้าตรวจรายงานได้ · `role` บทบาท (ประธาน, เลขา, กรรมการ/สมาชิก, ผู้เข้าร่วมที่ไม่ใช่กรรมการ) · `attendance` สถานะการเข้าร่วม (เชิญแล้ว/เข้าร่วม/ไม่มา) ระบบตั้งเป็น "เข้าร่วม" ให้เมื่อพบเสียงพูดของคนนั้น · `absence_reason` สาเหตุที่ไม่มา แสดงเป็นหมายเหตุของผู้ไม่มาประชุมในรายงาน · `source` ที่มาของรายชื่อ

**ตาราง Transcript_Segments** เพิ่ม: `original_text` ข้อความต้นฉบับที่บอทจับได้ (เก็บเมื่อมีการแก้ไข) · `edited_at` เวลาแก้ไขล่าสุด · `deleted` ลบแบบซ่อน กู้คืนได้ ข้อความที่ลบจะไม่ถูกส่งให้ AI
หมายเหตุ: 1 แถว = 1 ประโยคที่จบแล้ว บันทึกทันที (ไม่ใช่เขียนทีเดียวตอนจบประชุม) ผู้พูดที่พูดยาวเกิน 3,000 ตัวอักษรต่อเนื่องจะถูกแบ่งเป็นหลายแถว

**ตาราง Summaries (แก้เป็น):** รายงานการประชุม 1 ฉบับต่อ 1 การประชุม (meeting_id เป็น UNIQUE) เก็บ `executive_summary` สรุปภาพรวม, `other_matters` เรื่องอื่น ๆ, `ai_snapshot` ฉบับที่ AI ร่างไว้เดิมเพื่อเทียบกับฉบับที่มนุษย์แก้, `model_used` และ `prompt_version` เพื่อตรวจย้อนหลังว่าใช้โมเดลและ prompt ใด, `edited_at` เวลาที่มนุษย์แก้ล่าสุด, `approved_by`/`approved_at` ผู้อนุมัติและเวลา (ไม่ว่าง = รายงานถูกล็อก)

**ตารางใหม่ Agenda_Items:** เก็บวาระและมติของแต่ละวาระที่ AI ร่างและมนุษย์แก้ไข ประกอบด้วย `order_no` ลำดับ, `title` หัวข้อ, `discussion` สรุปการอภิปราย, `resolution` มติ (ว่าง = ไม่มีมติ ได้แก่แจ้งเพื่อทราบหรือยังไม่ตัดสินใจ), `evidence` ข้อความอ้างอิงจาก transcript ที่รองรับ

**ตาราง Action_Items** เพิ่ม: `evidence` ข้อความอ้างอิงจาก transcript ที่รองรับงานนี้ ใช้ตรวจว่า AI ไม่ได้แต่งขึ้นเอง (`assignee` เป็น VARCHAR(100) ให้ตรงกับชื่อผู้เข้าร่วม)

6. **ทดสอบตัวจับคำบรรยายกับ Meet จำลอง 10 นาที** — พูดทั้งหมด 123 ประโยค จับได้ครบทุกประโยคและข้อความตรงกับที่พูด (ผิด 0 ประโยค) JS heap 0.8 → 0.8 MB (เปลี่ยน +0.08 MB) จำนวน DOM node 22 → 19 และตัวฟังเหตุการณ์ (listener) 0 → 0 แสดงว่าไม่มีหน่วยความจำสะสมในส่วนนี้ นอกจากนี้ชุดทดสอบ watchdog 5 กรณี (ปกติ ประชุมจบ หน้าถูกปิด หน้าโหลดใหม่ ครบเวลาสูงสุด) ผ่านทุกกรณี
7. **ทดสอบชุดวัดคุณภาพ AI กับบทประชุมจำลอง (ข้อความสะอาด) 3 รอบ** — โมเดล `gemini-3.5-flash` พร้อม prompt `minutes_v2` ผ่านเกณฑ์ทั้ง 9 ตัวชี้วัด (ครบถ้วนของวาระ 100% ความถูกต้องของมติ 100% มติที่แต่งขึ้น 0% ครบถ้วนของงาน 100% ผู้รับผิดชอบถูกคน 100% วันกำหนดถูกต้อง 100% อ้างอิงไม่ได้ 0% ผิดแต่ตรวจไม่เจอ 0) *หมายเหตุ: ข้อมูลทดสอบเป็นบทสนทนาที่เขียนขึ้น ไม่ใช่ประชุมจริง และเป็นเพียง 3 รอบ จึงยังสรุปคุณภาพกับการประชุมจริงไม่ได้*
