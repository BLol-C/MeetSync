# ส่วน 1 อ่านโค้ดทีละจุด

เปิดไฟล์ตามที่ระบุ อ่านเรียงลำดับ ตัวหนาคือ "จุดที่ควรชี้ให้อาจารย์ดู"

## 1.1 การตรวจจับผู้เข้าร่วมจาก Meet (อาจารย์ขอดูโดยเฉพาะ)

**โจทย์:** คนที่เข้าห้องแต่ไม่พูด จะรู้ได้อย่างไรว่าเข้าร่วม ระบบอ่านรายชื่อจากแผง "บุคคล" ของ Meet แล้วจับคู่กับรายชื่อที่ลงทะเบียนไว้ ลำดับการทำงาน:

```
meet_engine._monitor  (ลูปเฝ้าทุก 15 วินาที)   meet_engine.py:501
   └─ ทุก 60 วินาที (และทันทีที่เข้าห้อง)  → _scan_participants   :470
        └─ page.evaluate(JS_READ_PARTICIPANTS)  :228-261   อ่านชื่อจาก DOM
        └─ _emit(type="participants", names=[...])
bot_service._handle_event  (branch "participants")  :173-177   ใส่คิว
   └─ _save_worker_loop  :148
        └─ _persist_participants  :139
             └─ db.record_room_names  db.py:675
                  ├─ mark_present_by_names  :655   ชื่อตรง → "เข้าร่วม"
                  └─ ชื่อไม่ตรงใคร → สร้างแถวใหม่ source='meet'   :686-698
```

**ขั้น 1: อ่านชื่อจากหน้า Meet** (`bot/meet_engine.py:228-261` `JS_READ_PARTICIPANTS`)
- บรรทัด 231: `labelRe` รายชื่อคำที่ป้ายของรายการอาจเป็น ("participants", "people", "บุคคล", "ผู้เข้าร่วม" ฯลฯ) บรรทัด 232 `waitingRe` กันรายการ "คนที่รออนุญาต" ไม่ให้ปนเป็นคนที่อยู่ในห้อง
- บรรทัด 233-237: หา `[role="list"]` ทั้งหมดในหน้า เลือกอันที่ป้ายตรงรูปแบบและไม่ใช่รายการรอ
- บรรทัด 238-244: ถ้าไม่พบแผง ส่งกลับ `panel: false` พร้อมรายการที่เห็น (ไว้ใช้ปรับ selector ตามหน้าจริง ไม่ใช่การเดา)
- บรรทัด 246-257: วนทุก `[role="listitem"]` เอาชื่อจาก `aria-label` ถ้าไม่มีใช้ข้อความท้ายสุดในรายการ **บรรทัด 249 ข้ามแถวที่มี "(คุณ)" หรือ "(You)" = แถวของบอทเอง ไม่นับเป็นผู้เข้าร่วม** และตัดชื่อซ้ำ ชื่อยาวเกิน 100 ตัวอักษรไม่เอา

**ขั้น 2: เปิดแผงถ้ายังไม่เปิด** (`:470-490` `_scan_participants`)
- ถ้า `panel` เป็นเท็จ และยังพยายามไม่ครบ 2 ครั้ง (`PEOPLE_OPEN_ATTEMPTS` `:274`) บอทหาปุ่ม "บุคคล" แล้วกดเปิดแผง (เลือกด้วยข้อความของปุ่ม เพราะ `jsname="ocqpFe"` ใช้ร่วมกันหลายปุ่ม ตามคอมเมนต์บรรทัด 262-263) แล้วอ่านใหม่
- อ่านได้ → ส่ง event `participants` พร้อมรายชื่อ อ่านไม่ได้ติดกัน 2 ครั้ง → ส่งสถานะเตือนครั้งเดียวว่าอ่านรายชื่อไม่ได้ **การอ่านรายชื่อพลาดไม่กระทบการจับคำบรรยาย** (บรรทัด 578-579 กลืน exception)

**ขั้น 3: ตั้งเวลาอ่าน** (`:523-525`, `:569-575` ใน `_monitor`)
- `last_scan = started - PARTICIPANT_SCAN_S` ทำให้ **รอบแรกอ่านทันทีที่เข้าห้อง** แล้วอ่านซ้ำทุก 60 วินาที (ค่า `BOT_PARTICIPANT_SCAN_S`) เหตุผลที่เขียนไว้ในคอมเมนต์: ถ้ารอรอบแรกอีก 60 วินาที ประชุมสั้นหรือคนที่เงียบจะไม่ถูกอ่านเลย (ปัญหาที่เจอจริงตอนทดลอง)
- ตอนสั่งหยุดบอท `_final_scan` (`:492`) อ่านอีกรอบ จำกัดเวลา 4 วินาที (`FINAL_SCAN_TIMEOUT_S`) จับคนที่เข้าหลังรอบสแกนล่าสุด

**ขั้น 4: จับคู่ชื่อและตั้งสถานะ** (`db.py:655-720`)
- `_find_speaker_for_name` (`:708`): **จับคู่เฉพาะ "ชื่อภาษาอังกฤษ" (`meet_alias`) ที่ลงทะเบียนไว้** (ถ้าแถวไหนไม่มี alias ใช้ชื่อหลักของแถว) ลองตรงตัวก่อน ถ้าไม่เจอลองเทียบแบบไม่สนตัวพิมพ์/ช่องว่าง `normalize_name` และ **ยอมรับเฉพาะกรณีตรงคนเดียว ถ้ากำกวมหลายคนจะไม่เดา** (บรรทัด 719-720 คืน `None`)
- `mark_present_by_names` (`:655`): ถ้าจับคู่ได้ ตั้ง `seen_in_room = TRUE` (หลักฐานว่าบอทเห็นในห้อง) และเปลี่ยน `attendance` จาก `invited` เป็น `present` **เปลี่ยนเฉพาะคนที่ยัง "เชิญไว้"** คนที่ผู้ใช้ตั้ง "ไม่มา" ไว้เองไม่ถูกเปลี่ยน (บรรทัด 667 เงื่อนไข `attendance = 'invited'`)
- `record_room_names` (`:675`): ชื่อที่ไม่ตรงใครเลย สร้างเป็นแถวใหม่ `role = guest, attendance = present, source = 'meet', seen_in_room = TRUE` ให้ผู้ใช้เลือกที่แท็บ ③ ว่าเป็นใคร (จับคู่กับคนที่ลงทะเบียน / ผู้มาประชุมทั่วไป / ไม่นับในรายงาน) ชื่อที่ผู้ใช้จับคู่แล้วระบบจำไว้ ครั้งหน้าตรงเอง

**ขั้น 5: ผู้ใช้ยืนยัน** (`ui/tab_transcript.py:54` `_confirm_section`, `db.py:892` `list_unresolved`, `service.py:421` `verify_transcript`)
- ก่อนยืนยัน transcript ต้องตอบให้ครบ: ชื่อจาก Meet ที่ยังไม่จับคู่ และคนที่ลงทะเบียนไว้แต่ยัง "เชิญไว้" ระบบไม่ให้ไปต่อจนกว่าจะตอบครบ "ไม่มา" ผู้ใช้เป็นคนยืนยัน (มีข้อยกเว้นเล็กน้อยตอนอนุมัติ ดู `docs/TOR_MAP.md` หัวข้อ "ข้อควรรู้" ข้อ 5)

**จุดที่ควรรู้ไว้ก่อนอาจารย์ถาม**
- คอมเมนต์บรรทัด 226 เขียนว่า "บอทกดเปิดแผงเองด้วยปุ่มนี้ยังไม่ได้ทดสอบกับห้องจริง" ซึ่งเก่ากว่า Proposal หน้า 70 ที่บอกว่าทดสอบกับห้อง Meet จริง 1 ห้อง 2 คนแล้ว (ถ้าอาจารย์เปิดโค้ดเจอ ให้บอกว่าคอมเมนต์เขียนก่อนทดสอบ)
- โครงสร้างหน้า Meet ไม่มีเอกสาร API และ Google เปลี่ยนได้ไม่แจ้ง นี่คือความเสี่ยงที่เขียนไว้เป็นข้อจำกัดอยู่แล้ว
- เทสต์: `tests/test_participant_scan.py` (8 ข้อ) ทดสอบกับหน้า Meet จำลองใน Chromium จริง

## 1.2 การดักจับคำบรรยายสด (ฟังก์ชัน 2)

**โจทย์:** Meet ส่งคำบรรยายเป็นแถวๆ ในกล่องบนหน้าจอ ข้อความในแถวถูกเติม ถูกแก้ และถูกตัดหัวทิ้งตลอดตอนคนพูดยาว ต้องได้ข้อความที่ถูกต้องและไม่ซ้ำ

อ่านเรียง (`bot/meet_engine.py`, สคริปต์ JavaScript ที่ฝังในหน้า Meet บรรทัด 29-221):
1. **บรรทัด 201-202 `MutationObserver`**: เฝ้ากล่องคำบรรยาย ทุกครั้งที่ข้อความเปลี่ยน เรียก `scan` (บรรทัด 140)
2. **บรรทัด 164-185 (ใน `scan`)**: ให้แต่ละแถวมี id นับต่อกัน อ่านข้อความดิบ (`raw`) เทียบกับของเดิม ถ้าเปลี่ยน เรียก `updateCommit` ส่ง event "ยังไม่ final" ได้ไม่ถี่กว่าทุก 250 มิลลิวินาทีต่อแถว (`EMIT_THROTTLE_MS` บรรทัด 39) แล้วตั้งตัวจับเวลา 1.5 วินาที (`FINALIZE_MS` บรรทัด 38) ถ้าแถวนั้นเงียบไป 1.5 วินาที ถือว่าจบประโยค ส่ง event `final`
3. **บรรทัด 81-115 `mergeCommit` (จุดที่ควรชี้):** ปัญหาคือ Meet ตัดข้อความหน้าทิ้ง (sliding window) และ ASR แก้คำย้อนหลัง ถ้าเอาข้อความใหม่ไปต่อท้ายข้อความเก่าตรงๆ จะซ้ำ วิธีที่ใช้คือหา "จุดยึด" (ข้อความสั้น 8 ตัวอักษรที่ตรงกันเป๊ะ) ระหว่างข้อความใหม่กับของสะสม แล้วให้ข้อความใหม่ทับตั้งแต่จุดนั้น ถ้าหาจุดทับซ้อนไม่เจอ เลือกอันที่ยาวกว่า ไม่ต่อกัน ("ยอมเสี่ยงหลุดคำเก่าดีกว่าคำซ้ำ" ตามคอมเมนต์บรรทัด 112-113) เทสต์: `tests/test_caption_watcher.py`
4. **บรรทัด 130-136 `cleanup`:** เมื่อแถวจบ ลบข้อมูลของแถวนั้นออกจากทุก `Map` และยกเลิกตัวจับเวลา (นี่คือกลไกกันหน่วยความจำสะสมในหน้า Meet)
5. **บรรทัด 193-204 `attach`:** ถ้า Meet สร้างกรอบคำบรรยายใหม่ (เปลี่ยน layout) ตัดตัวสังเกตเก่าทิ้ง ปิดจบแถวที่ค้าง แล้วผูกกับกรอบใหม่ (ไม่งั้นตัวสังเกตเก่าสะสมตลอดประชุมยาว)

ฝั่ง Python เมื่อได้ event (`bot_service.py`):
- `_handle_event` (`:162`, branch `caption` `:178-198`): เก็บแถวสดไว้ให้หน้าเว็บอ่านไม่เกิน 150 แถว (`_LIVE_ROWS_MAX`) และเมื่อ `final` ใส่คิวเขียน DB
- `_save_worker_loop` (`:148`): worker ตัวเดียว เขียนลง MySQL ทีละรายการ ผ่าน `asyncio.to_thread` เพราะ PyMySQL เป็นแบบ sync
- `_persist_segment` (`:99`): แถวเดียวกันที่ final ซ้ำ (คนเดิมพูดต่อ) → `update` แถวเดิม ไม่ insert ซ้ำ ข้อความเกิน 3,000 ตัวอักษรตัดเป็น segment ใหม่ที่ช่องว่าง (`_cut_point` `:92`)

หมายเหตุ: ตัวแปร `_gone_rows` (`bot_service.py:59`) เป็นชุดตัวเลขที่เพิ่มขึ้นเรื่อยๆ ตลอดการประชุม ไม่มีเพดาน (ล้างเฉพาะตอนเริ่มบอทใหม่ `:299`) เล็กมาก (ตัวเลข id แถว) ผมไม่ได้วัดว่ามีผลต่อหน่วยความจำจริงหรือไม่

## 1.4 AI ร่างรายงาน (ฟังก์ชัน 4)

อ่านเรียง:
1. `service.py:548` `generate_report` ตรวจว่ายืนยัน transcript แล้ว → เรียก `reports/summarizer.py:517` `generate_for_meeting`
2. `generate_for_meeting` (`:517-542`): ดึง transcript (ไม่รวมช่วงที่ลบ) และผู้เข้าร่วม (ไม่รวมที่ผู้ใช้ตัดออก) → **`continuity.prefill_items` สร้างโครงวาระ 2, 3, 4.1 จากรายงานครั้งก่อน** (บรรทัด 531) → ส่งเข้า `generate_minutes_content` → `apply_carried` เติมสิ่งที่ AI ตอบ → `db.save_report`
3. `generate_minutes_content` (`:435-494`): ถ้า transcript ไม่เกิน 60,000 ตัวอักษร ส่งครั้งเดียว ถ้ายาวกว่าแบ่งช่วงละ 30,000 สกัดบันทึกย่อก่อน (map-reduce `:459-470`) แล้วเรียบเรียง บังคับรูปแบบด้วย `response_schema` (บรรทัด 487 ส่ง `MinutesBodyAI`) ถ้า AI ตอบนอกรูปแบบ ลองใหม่หนึ่งครั้ง (`:485-491`) แล้ว **`validate_minutes` (`:492` เรียก, `:187` นิยาม)** ตรวจผล
4. **`validate_minutes` / `grounding_score` (`:187`, `:130`) (จุดที่ควรชี้):** AI ไม่ถูกเชื่อตรงๆ ทุกมติและงานต้องมีข้อความอ้างอิงที่ "หาเจอใน transcript จริง" (ทนต่อการเว้นวรรคไทย เกณฑ์ `GROUNDED_THRESHOLD` = 0.8) ผู้รับผิดชอบต้องจับคู่กับรายชื่อได้ วันที่ต้องถูกต้อง ไม่ผ่านจะใส่คำเตือนให้คนตรวจ ไม่ใช่ลบทิ้ง
5. `reports/continuity.py`:
   - `prefill_items` (`:81`): งานทุกรายการของรายงานครั้งก่อน → วาระ 3, วาระ 2 หนึ่งรายการ, และวาระที่ไม่มีมติของครั้งก่อน → วาระ 4.1 ให้รหัส R1, R2, ...

# ส่วน 2 คำอธิบายพร้อมพูด (ฟังก์ชันละ 5–6 ประโยค)

เขียนเป็นภาษาพูด ปรับสำนวนเองได้ ไม่เกินที่ระบบทำจริง

**ฟังก์ชัน 1: เชื่อมต่อห้องประชุมและดักจับคำบรรยายสด**
ผู้จัดประชุมใส่ลิงก์ Google Meet ในหน้าเว็บ ระบบตรวจรูปแบบลิงก์แล้วบันทึกการประชุม จากนั้นกดเริ่มบอท หน้าเว็บส่งคำสั่งไปที่บริการบอทผ่าน HTTP พร้อมโทเคนลับ บอทใช้ Playwright เปิด Chrome ที่ล็อกอินบัญชี Google ไว้ เข้าห้อง และรอให้ผู้จัดประชุมกดอนุญาต (รอได้สูงสุด 20 นาที) พอเข้าห้องแล้วบอทเปิดคำบรรยายสด และตรวจจากหน้าจอจริงว่าเปิดสำเร็จ ระหว่างประชุมมี watchdog ตรวจทุก 15 วินาทีว่าหน้า ตัวจับคำบรรยาย และปุ่มวางสายยังอยู่ ถ้าหลุดห้องหรือประชุมจบ จะปิดการบันทึกอย่างเรียบร้อยและข้อความที่บันทึกแล้วไม่หาย

**ฟังก์ชัน 2: ดักจับและจัดระเบียบข้อความคำบรรยายสด**
ตัวจับเป็น JavaScript ที่ฝังในหน้า Meet ใช้ MutationObserver เฝ้ากล่องคำบรรยาย เมื่อแถวเงียบไป 1.5 วินาทีถือว่าจบประโยค แล้วส่งข้อความกับชื่อผู้พูดให้บริการบอท ซึ่งเขียนลง MySQL ผ่านคิวที่มี worker ตัวเดียว ข้อความที่ยาวเกิน 3,000 ตัวอักษรแบ่งเป็นหลาย segment ระบบใช้ "จุดยึด" แก้ปัญหาที่ Meet ตัดข้อความหน้าแล้วแก้คำย้อนหลังไม่ให้ข้อความซ้ำ ไม่เก็บไฟล์เสียง เก็บเฉพาะข้อความ ส่วนรายชื่อผู้เข้าร่วม บอทอ่านจากแผง "บุคคล" ของ Meet ทันทีที่เข้าห้อง ทุก 60 วินาที และตอนหยุดบอท แล้วตั้งสถานะ "เข้าร่วม" ให้คนที่ชื่อภาษาอังกฤษตรงกับที่ลงทะเบียนไว้ ถ้าชื่อไม่ตรงระบบไม่เดา เก็บเป็นชื่อนอกรายชื่อให้ผู้ใช้ตัดสินเอง

**ฟังก์ชัน 3: ตรวจทานและยืนยันข้อความถอดเสียง**
หลังประชุมจบ ผู้ใช้เปิดแท็บ transcript แก้ข้อความ เปลี่ยนผู้พูด หรือลบช่วงที่ไม่เกี่ยวข้อง ข้อความต้นฉบับเก็บไว้ใน `original_text` ช่วงที่ลบเป็นแบบซ่อนและกู้คืนได้ และไม่ถูกส่งให้ AI ชื่อที่ Meet แสดงต่างจากรายชื่อ ผู้ใช้รวมเข้ากับคนที่ถูกต้องได้ ก่อนยืนยัน ผู้ใช้ต้องตอบเรื่องผู้เข้าร่วมให้ครบทุกคน (มา ไม่มา จับคู่ หรือเป็นผู้มาประชุมทั่วไป) ถ้ายังตอบไม่ครบ ระบบไม่ให้ยืนยัน และถ้ายังไม่ยืนยัน transcript ระบบไม่ให้ AI สร้างรายงาน เพราะเราต้องการให้คนตรวจข้อมูลต้นทางก่อนทุกครั้ง

**ฟังก์ชัน 4: AI สรุปเนื้อหาและสกัดภาระงาน**
ระบบส่ง transcript ที่ยืนยันแล้วให้ Gemini พร้อมวันที่ประชุมจริงเพื่อแปลง "วันพฤหัสหน้า" เป็นวันที่ และบังคับรูปแบบคำตอบด้วย response schema (สรุป วาระ มติ ภาระงาน ผู้รับผิดชอบ กำหนดส่ง) ถ้า transcript ยาวเกิน 60,000 ตัวอักษรจะแบ่งช่วงสกัดก่อนแล้วเรียบเรียงรวม หลัง AI ตอบ ระบบไม่เชื่อตรงๆ ทุกมติและงานต้องมีข้อความอ้างอิงที่หาเจอใน transcript จริง ผู้รับผิดชอบต้องอยู่ในรายชื่อ ไม่ผ่านจะติดคำเตือนให้คนตรวจ วาระ 2, 3, 4.1 ระบบสร้างโครงจากรายงานครั้งก่อนที่อนุมัติแล้ว ให้ AI เติมความคืบหน้าและมติเฉพาะที่พูดถึงจริงและมีหลักฐาน ผลลัพธ์เป็นฉบับร่างเสมอ

**ฟังก์ชัน 5: แสดงผลสรุปสำหรับตรวจสอบ**
ผลที่ AI ร่างถูกบันทึกลง MySQL ทันที และแสดงบนหน้าเว็บให้ผู้ใช้แก้ได้ทุกช่อง (สรุป วาระ มติ เรื่องอื่นๆ และภาระงาน) พร้อมคำเตือนและหลักฐานที่ตรวจกับ transcript แล้ว (เครื่องหมาย ถูก/เตือน) คำนวณสดทุกครั้งที่เปิดดู ทุกครั้งที่ AI ร่าง ผู้ใช้บันทึกแก้ อนุมัติ หรือยกเลิกอนุมัติ ระบบเก็บเป็นฉบับใหม่ในตารางประวัติ แบบเพิ่มอย่างเดียว ไม่เขียนทับฉบับเดิม ผู้ใช้เปิดดู เปรียบเทียบกับฉบับก่อนหน้า และเลือกฉบับเก่ากลับมาใช้ได้ขณะเป็นฉบับร่าง รายงานที่อนุมัติแล้วถูกล็อก ต้องยกเลิกอนุมัติก่อนจึงแก้ได้

**ฟังก์ชัน 6: ส่งออกและแจ้งเตือนภาระงานภายนอก**
เมื่อผู้ใช้กดอนุมัติ ระบบส่งภาระงานที่มีวันกำหนดเข้า Google Calendar ของผู้อนุมัติพร้อมกัน ผ่าน OAuth 2.0 ด้วยสิทธิ์ระดับกิจกรรมเท่านั้น รองรับนัดวันเดียว หลายวัน และช่วงเวลา ถ้างานไหนส่งไม่สำเร็จ งานอื่นไม่ล้ม และกดส่งซ้ำเฉพาะงานที่ค้างได้ ผู้รับผิดชอบที่มีอีเมลในรายชื่อถูกเพิ่มเป็นผู้ร่วมนัด แต่ส่งอีเมลเชิญจริงเมื่อผู้ใช้ติ๊กเลือกเท่านั้น ถ้าผู้ใช้แก้ชื่อหรือเวลาใน Calendar เอง ระบบตรวจให้เมื่อเปิดหน้าหรือกดปุ่ม และปรับงานตามเมื่อผู้ใช้ยืนยัน (ไม่ใช่เรียลไทม์) รายงานดาวน์โหลดเป็น PDF ตามแบบฟอร์ม ฟอนต์ TH Sarabun New ยังไม่อนุมัติมีลายน้ำ "ฉบับร่าง" และเปิดดูประวัติการประชุมย้อนหลังได้

# ส่วน 3 แบบฝึกถามตอบ (ปิดเฉลยแล้วตอบเอง)

วิธีใช้: อ่านคำถามทีละข้อ พูดคำตอบออกเสียง แล้วค่อยดูเฉลยและตำแหน่งโค้ด ข้อที่ตอบไม่ได้ให้กลับไปอ่านส่วน 1 ตามตำแหน่ง ข้อ 1–8 ง่าย 9–18 กลาง 19–26 ยาก/คำถามกับดัก

## ฟังก์ชัน 1–2: บอทและการดักจับ

1. **บริการบอทกับหน้าเว็บคุยกันอย่างไร และทำไมต้องมีโทเคน?**
   เฉลย: HTTP ในเครื่อง (127.0.0.1 พอร์ต 8000) แนบโทเคนลับทุกคำขอ ผู้ใช้ที่ล็อกอินถูกส่งในเฮดเดอร์ บริการบอทรับเฉพาะคำขอที่มีโทเคนถูกต้อง และตรวจสิทธิ์ผู้ใช้ต่อการประชุมทุกครั้ง (`bot/botclient.py:25` `get_token`, `bot_service.py:242` `identity`, `:260` `_manager_of`) เทสต์ `test_requests_without_the_secret_token_are_rejected`
2. **บอทเข้าห้องอย่างไร ถ้าผู้จัดยังไม่อนุญาต?**
   เฉลย: Playwright เปิด Chrome แบบ persistent profile (`.meet_profile/`) กดปุ่มเข้าร่วม (`meet_engine.py:654`) แล้วรอได้สูงสุด 1200 วินาที (`JOIN_WAIT_S` `:283`) ผู้จัดต้องกดอนุญาตเอง
3. **ระบบรู้ได้อย่างไรว่าเปิดคำบรรยายสำเร็จ?**
   เฉลย: ตรวจจากหน้าจอจริง (เห็นกรอบคำบรรยาย หรือปุ่มเปลี่ยนเป็น "ปิดคำบรรยาย") ก่อนรายงานสำเร็จ และวนลองใหม่จนผู้จัดอนุญาต (`_caption_state` `:372`, `_enable_captions` `:401`, `_ensure_captions` `:424`)
4. **ตัวจับคำบรรยายทำงานอย่างไรโดยย่อ?**
   เฉลย: JavaScript ฝังในหน้า Meet ใช้ MutationObserver (`meet_engine.py:201`) เมื่อแถวเงียบ 1.5 วินาทีถือว่าจบประโยคแล้วส่งเข้า Python
5. **ปัญหา sliding window คืออะไร แก้อย่างไร?**
   เฉลย: Meet ตัดหัวข้อความในแถวทิ้ง และ ASR แก้คำย้อนหลัง ถ้าต่อท้ายตรงๆ จะซ้ำ ใช้ "จุดยึด" 8 ตัวอักษรหาจุดทับซ้อนแล้วให้ข้อความใหม่ทับตั้งแต่จุดนั้น (`mergeCommit` `:94-115`) เทสต์ `test_caption_watcher`
6. **ข้อความยาวเกินคอลัมน์ฐานข้อมูลทำอย่างไร?**
   เฉลย: เกิน 3,000 ตัวอักษรตัดเป็น segment ใหม่ที่ช่องว่าง ไม่ตัดกลางคำ (`bot_service.py:35`, `:92` `_cut_point`, `:99` `_persist_segment`) เทสต์ `test_one_endless_monologue_is_split_into_segments_not_lost`
7. **ทำไมคิวเขียน DB มี worker ตัวเดียว?**
   เฉลย: ให้ลำดับการเขียนถูกต้อง และ PyMySQL เป็นแบบ sync ต้องรันใน thread ไม่บล็อก event loop (`_save_worker_loop` `:148`)
8. **เก็บเสียงของผู้เข้าร่วมไหม?**
   เฉลย: ไม่เก็บ เก็บเฉพาะข้อความที่ Google ถอดให้ (ไม่มีโค้ดบันทึกเสียงที่ผมพบ)

## ตรวจจับผู้เข้าร่วม (จุดที่อาจารย์ขอดู)

9. **บอทอ่านรายชื่อคนในห้องเมื่อไร?**
   เฉลย: ทันทีที่เข้าห้อง ทุก 60 วินาที และตอนหยุดบอท (รอบสุดท้ายจำกัด 4 วินาที) (`meet_engine.py:523-525`, `:569-575`, `:492`)
10. **อ่านรายชื่อจากไหนในหน้า Meet?**
    เฉลย: แผง "บุคคล" หาจาก `[role="list"]` ที่ป้ายตรงรูปแบบ และไม่ใช่รายการ "รออนุญาต" แล้วอ่านชื่อจาก `listitem` (`:228-261`)
11. **ทำไมต้องข้ามแถวที่มี "(You)" หรือ "(คุณ)"?**
    เฉลย: เป็นแถวของบอทเอง ไม่ใช่ผู้เข้าร่วม (`:249`)
12. **ถ้าแผงรายชื่อยังไม่เปิด?**
    เฉลย: บอทกดปุ่ม "บุคคล" เปิดเอง พยายามได้ 2 ครั้ง ถ้าไม่ได้ส่งสถานะเตือนครั้งเดียว และไม่กระทบการจับคำบรรยาย (`_scan_participants` `:470-490`)
13. **จับคู่ชื่อใน Meet กับรายชื่อลงทะเบียนอย่างไร?**
    เฉลย: ด้วย "ชื่อภาษาอังกฤษ" (`meet_alias`) ตรงตัวก่อน ถ้าไม่เจอเทียบแบบไม่สนตัวพิมพ์/ช่องว่าง และยอมรับเฉพาะกรณีตรงคนเดียว กำกวมไม่เดา (`db.py:708-720`)
14. **ถ้าชื่อไม่ตรงใครเลย?**
    เฉลย: สร้างแถวใหม่ `source = 'meet'`, `role = guest`, `attendance = present` ให้ผู้ใช้เลือกที่แท็บ ③ (`db.py:686-698`) และ `list_unresolved` (`:892`) นับเป็นรายการค้างต้องตอบก่อนยืนยัน
15. **ระบบตั้ง "ไม่มา" ให้อัตโนมัติไหม?**
    เฉลย: ตอนอ่านรายชื่อ ไม่ตั้ง มีแต่ "เข้าร่วม" และเปลี่ยนเฉพาะคนที่ยัง "เชิญไว้" (`db.py:667`) ผู้ใช้ต้องตอบทุกคนก่อนยืนยัน transcript ข้อยกเว้น: คนที่เพิ่มรายชื่อหลังยืนยันแล้วยังเป็น "เชิญไว้" ระบบตั้ง "ไม่มา" ตอนอนุมัติ (`service.py:606`)
16. **ทำไมอ่านรอบแรกทันทีที่เข้าห้อง ไม่รอ 60 วินาที?**
    เฉลย: ประชุมสั้นหรือคนที่เข้าแล้วเงียบจะไม่ถูกอ่านเลย (ปัญหาที่เจอตอนทดลอง) `last_scan = started - PARTICIPANT_SCAN_S` (`:525`)
17. **อ่านรายชื่อไม่ได้เกิดอะไร?**
    เฉลย: แจ้งสถานะครั้งเดียว ผู้ใช้ตั้ง "เข้าร่วม" เองที่แท็บ ① การจับคำบรรยายไม่ได้รับผลกระทบ (`:578-579`)
18. **ผ่านการทดสอบกับห้องจริงหรือยัง?**
    เฉลย: ทดสอบกับ Meet จริง 1 ห้อง 2 คน (Proposal หน้า 70) และหน้าจำลองใน Chromium (`tests/test_participant_scan.py` 8 ข้อ) ยังไม่ได้ทดสอบกับห้องที่มีผู้เข้าร่วมจำนวนมาก

## ฟังก์ชัน 3–6: transcript, AI, ประวัติ, Calendar

19. **ทำไมต้องยืนยัน transcript ก่อนให้ AI?**
    เฉลย: ให้คนตรวจข้อมูลต้นทางก่อน ถ้ายังไม่ยืนยันหรือยังตอบเรื่องผู้เข้าร่วมไม่ครบ `generate_report` ไม่ทำงาน (`service.py:421` `verify_transcript`, `:548`)
20. **AI ถูกบังคับให้ตอบรูปแบบไหน และถ้าตอบผิดรูปแบบ?**
    เฉลย: `response_schema` แบบ pydantic (`MinutesBodyAI` `summarizer.py:82`, ส่งที่ `:487`) ถ้าตอบนอกรูปแบบ ลองใหม่หนึ่งครั้งแล้วแจ้งผู้ใช้ (`:485-491`) เทสต์ `test_bad_ai_output_is_retried_once`
21. **ระบบกันไม่ให้ AI แต่งมติหรืองานได้อย่างไร?**
    เฉลย: ทุกมติและงานต้องมีข้อความอ้างอิงที่หาเจอใน transcript จริง คะแนน ≥ 0.8 (`grounding_score` `:130`, `GROUNDED_THRESHOLD` `:49`) ไม่ผ่านติดคำเตือน เทสต์ `test_fabricated_evidence_is_flagged`
22. **วาระ 2, 3, 4.1 มาจากไหน และ AI เกี่ยวอย่างไร?**
    เฉลย: ระบบสร้างโครงจากรายงานครั้งก่อนที่อนุมัติแล้ว (ข้อเท็จจริงจาก DB) ให้ AI เติมความคืบหน้า/มติเฉพาะที่พูดจริงและมีหลักฐาน เติมรายการที่ไม่มีในโครงไม่ได้ (`continuity.py:81`, `:118`) ประชุมครั้งแรก (ไม่เลือกครั้งก่อน) วาระเหล่านี้ว่าง
23. **ถ้างานของ AI มีผู้รับผิดชอบที่ไม่อยู่ในรายชื่อ?**
    เฉลย: ติดคำเตือน (`match_participant_name` `summarizer.py:150`, `validate_minutes`) คนตรวจแก้ก่อนอนุมัติ
24. **ประวัติการแก้ไขเก็บอย่างไร และถ้าเลือกฉบับเก่า?**
    เฉลย: ตาราง `summary_versions` เพิ่มอย่างเดียว (`db.py:1218` `_record_version`) เลือกฉบับเก่ามาใช้ขณะเป็นฉบับร่างเปลี่ยนตัวชี้ `current_version_no` ไม่สร้างฉบับใหม่ (`db.py:1421`, `service.py:534`)
25. **ถ้าส่ง Calendar งานหนึ่งล้มเหลว (เช่นอีเมลผู้รับผิดชอบผิด) เกิดอะไร?**
    เฉลย: งานนั้นขึ้นเป็นส่งไม่สำเร็จ งานอื่นส่งต่อไป ไม่ย้อนการอนุมัติ ผู้ใช้แก้แล้วกด "ส่งงานที่ยังไม่ส่ง" (`service.py:690-708`, `:751` `approve_and_send`) เจอจริงวันที่ 11 พ.ย. 2569 ระบบยังไม่ข้ามอีเมลผิดให้เอง
26. **ผู้รับผิดชอบจะได้อีเมลเชิญไหม?**
    เฉลย: เพิ่มเป็นผู้ร่วมนัดถ้ามีอีเมลในรายชื่อ แต่ส่งอีเมลเชิญจริงเฉพาะเมื่อผู้ใช้ติ๊ก (`sendUpdates` เป็น `all` เมื่อติ๊ก ไม่งั้น `none`, `calendar_sync.py:124`) ค่าเริ่มต้นกันอีเมลหลุดไปหาคนจริงตอนทดลอง

## ข้อทดสอบกับดัก (ถามเพื่อดูว่ารู้ข้อจำกัดไหม)

27. **"ระบบนี้ไม่มี memory leak ใช่ไหม?"** → ดูตารางห้ามพูดเกินจริงข้างบน
28. **"ทดสอบ 1 ชั่วโมงแล้วผ่านทั้งหมดใช่ไหม?"** → ผ่านเกณฑ์ที่ใช้ (ท้ายไม่สูงกว่าต้นเกิน 15%) ทั้งสองรอบ แต่เกณฑ์นี้มองไม่เห็นการไต่ช้าๆ ช่วงท้าย และวัดรวมทั้งเครื่อง
29. **"AI เติมวาระ 2, 3, 4.1 ถูกทุกครั้งหรือไม่?"** → ไม่รับรอง ผลเป็นฉบับร่าง ต้องตรวจ อาจสร้างรายการซ้ำหรือใส่ผู้รับผิดชอบผิดคนได้ (เจอจริงในการทดสอบ)
30. **"ถ้าไม่ได้เชิญคนนอกแต่เขาเข้าห้องล่ะ?"** → ขึ้นเป็นชื่อนอกรายชื่อให้ผู้ใช้ตัดสิน (ไม่นับในรายงานก็ได้) บอทเห็นได้เพราะอ่านจากแผงบุคคล

## คำแนะนำการซ้อม

1. ซ้อมกับตัวเอง 3 รอบ: รอบแรกดูเฉลย รอบสองปิดเฉลยตอบเอง รอบสามเปิดโค้ดตามตำแหน่งที่ตอบไม่ได้
2. ซ้อมเปิดไฟล์ให้ไว: ฟังก์ชัน 1 `bot_service.bot_start` → `meet_engine._run`, ฟังก์ชัน 2 `JS_CAPTION_WATCHER` และ `JS_READ_PARTICIPANTS`, ฟังก์ชัน 4 `validate_minutes`, ฟังก์ชัน 6 `service.approve_and_send`
3. เตรียมเปิดหน้าจอไว้: หน้าสร้างการประชุม, แท็บ ③ (ส่วนยืนยันผู้เข้าร่วม), แท็บ ④ (คำเตือนและหลักฐาน, ประวัติ), แท็บ ⑤ (ตารางงานและสถานะส่ง), PDF
4. ถ้าอาจารย์ถามเรื่องที่ไม่แน่ใจ ตอบว่า "ขออนุญาตเปิดโค้ดดู" แล้วเปิดตามส่วน 1 ดีกว่าเดา

## สิ่งที่ผมไม่ได้ตรวจในไฟล์นี้

- ข้อความในส่วน 2 และ 3 อธิบายจากโค้ดและผลทดสอบที่มี ผมไม่ได้รันทั้งระบบกับ Meet, Gemini และ Calendar จริงในรอบเขียนเอกสารนี้
- เวลาที่ประเมินในตารางต้นไฟล์เป็นการคาดการณ์ ไม่ได้จับเวลา
- ตัวเลขทดสอบหน่วยความจำมาจากไฟล์ CSV เดิมของวันที่ 12 และ 13 ต.ค. (ดู `docs/SOAK_GUIDE.md`)
