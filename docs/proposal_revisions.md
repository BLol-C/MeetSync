เรียงตามหน้าของ Proposal เดิม แต่ละหัวข้อ: **เดิม → แก้เป็น** ข้อความใน "แก้เป็น" คัดลอกไปวางได้
รายการที่มี `[ ... ]` คือช่องที่ต้องเติมจากผลทดสอบจริงของทีม — **ห้ามเติมตัวเลขที่ยังไม่ได้ทดสอบจริง**

## 0. สรุปว่าเปลี่ยนอะไร (ผูกกับข้อเสนอแนะของอาจารย์ 7 ข้อ)

| ข้อเสนอแนะ | สิ่งที่ปรับในระบบ |
|---|---|
| 1. ผลลัพธ์เป็น "รายงานการประชุม" ตามแบบฟอร์ม | AI ร่างรายงานตามโครงมาตรฐาน (หัวรายงาน, ผู้มาประชุม/ไม่มา, วาระและมติ, เรื่องอื่น ๆ, สรุป, ตารางงาน, ช่องลงชื่อ) ออกเป็น PDF |
| 2. ระบุผู้พูด + บทบาท | กำหนดบทบาทประธาน/เลขา/ผู้เข้าร่วม/ผู้ไม่มาประชุม ล่วงหน้า จับคู่ชื่อผู้พูดจาก Meet กับรายชื่อ |
| 3. ตรวจทาน/แก้ไขโดยคน | ตรวจและแก้ transcript ก่อนยืนยัน → AI ร่าง → คนแก้ → อนุมัติ (ล็อกหลังอนุมัติ) |
| 4. หน้าเว็บตั้งค่าบอท + สิทธิ์ + ประวัติ | หน้าเว็บ Streamlit: สร้างประชุมและตั้งค่าผู้เข้าร่วมก่อนสั่งบอท, สิทธิ์เจ้าของ/ประธาน/เลขา, หน้ารายการประชุมย้อนหลัง |
| 5. เสถียรภาพ ≥ 1 ชม. ไม่มี memory leak | บริการบอทแยกจากหน้าเว็บ, watchdog ตรวจสุขภาพ, ล้างตัวจับคำบรรยาย, บันทึกลงฐานข้อมูลต่อเนื่อง, เครื่องมือวัดหน่วยความจำ |
| 6. ควบคุมคุณภาพ AI + Prompt ในระบบ | ชั้นตรวจสอบผลของ AI, ชุดวัดคุณภาพเทียบเฉลยพร้อมเกณฑ์, ไฟล์ Prompt แยกตามเวอร์ชัน |
| 7. Workflow ฐานข้อมูล → AI → Calendar | คงเดิม และเพิ่มสถานะ "ส่งเข้า Calendar เรียบร้อย" |

## 1. ที่มาและความสำคัญ (หน้า 1) — ย่อหน้าสุดท้าย

**แก้เป็น:**
จากปัญหาดังกล่าวโครงงาน MeetSync จึงถูกพัฒนาขึ้น โดยใช้โปรแกรมอัตโนมัติ (Bot) เข้าร่วมห้องประชุม Google Meet แล้วเปิดใช้งานคำบรรยายสด (Closed Captions) ภาษาไทย เพื่อดักจับข้อความบทสนทนาแบบเรียลไทม์ และบันทึกลงฐานข้อมูลอย่างต่อเนื่อง จากนั้นให้ผู้ใช้ตรวจทานและแก้ไขข้อความถอดเสียง ก่อนนำไปประมวลผลด้วยปัญญาประดิษฐ์เพื่อร่าง **รายงานการประชุม** ตามแบบฟอร์ม (วาระ มติ และภาระงาน) ให้ประธานหรือเลขาตรวจสอบ แก้ไข และอนุมัติ แล้วจึงส่งออกเป็นไฟล์ PDF และส่งภาระงานไปยัง Google Calendar ช่วยลดภาระการจดบันทึกและติดตามงานของผู้เข้าร่วมประชุม โดยมีมนุษย์เป็นผู้ตัดสินใจขั้นสุดท้ายเสมอ

## 2. วัตถุประสงค์ (หน้า 2)

**เดิม:** 1. เพื่อพัฒนาระบบสารสนเทศสรุปการประชุมและมอบหมายงาน

**แก้เป็น:**
1. เพื่อพัฒนาระบบสารสนเทศสรุปการประชุมและมอบหมายงาน ที่จัดทำผลลัพธ์เป็นรายงานการประชุมตามแบบฟอร์ม
2. เพื่อให้ระบุผู้พูดและบทบาทของผู้เข้าร่วมประชุม (ประธาน เลขา ผู้เข้าร่วม ผู้ไม่มาประชุม) และมีขั้นตอนให้มนุษย์ตรวจทานและอนุมัติผลลัพธ์ของ AI
3. เพื่อให้ระบบบอททำงานต่อเนื่องในห้องประชุมได้อย่างเสถียรอย่างน้อย 1 ชั่วโมง โดยไม่เกิดหน่วยความจำรั่วไหล
4. เพื่อกำหนดเกณฑ์และวิธีวัดคุณภาพของรายงานที่ AI ร่าง

## 3. ขอบเขตของโครงงาน (หน้า 2)

**ข้อ 1, 2, 4, 5 คงเดิม** เพิ่มข้อ 6–8 และแก้ข้อ 3 ดังนี้

**ข้อ 3 เดิม** (ตัดวงเล็บที่ว่า "ยังไม่มีการบังคับสิทธิ์" และ "ยังไม่สามารถแก้ไขเนื้อหาสรุป") → **แก้เป็น:**

3. ระบบมีการแบ่งกลุ่มผู้ใช้งานและบทบาทในการประชุม ดังนี้
 3.1) **เจ้าของการประชุม (Host)**: ผู้ใช้หลักที่เข้าสู่ระบบเว็บของ MeetSync สร้างการประชุม กำหนดรายชื่อและบทบาทผู้เข้าร่วม เป็นผู้สั่งบอทเข้าห้องประชุมด้วยตนเองทุกครั้ง และต้องเป็นผู้อนุญาตให้บอทเข้าห้อง
 3.2) **ประธานและเลขาการประชุม**: ได้รับการกำหนดบทบาทในรายชื่อผู้เข้าร่วม และสามารถเข้าสู่ระบบด้วยบัญชี Google ที่ตรงกับอีเมลที่ลงทะเบียนไว้ เพื่อตรวจ แก้ไข และอนุมัติรายงานได้เช่นเดียวกับเจ้าของการประชุม (ระบบตรวจสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ ผู้เข้าร่วมทั่วไปและผู้ที่ไม่เกี่ยวข้องไม่สามารถเข้าถึงการประชุมได้)
 3.3) **ผู้เข้าร่วมประชุมทั่วไป**: ไม่ต้องเข้าใช้งานเว็บ เพียงเข้าร่วมห้อง Google Meet ตามปกติ คำพูดจะถูกบันทึกจาก Closed Captions โดยอัตโนมัติ
6. ระบบจัดทำ **รายงานการประชุม** ตามแบบฟอร์มมาตรฐานทั่วไป (ไม่ใช่แบบฟอร์มเฉพาะหน่วยงาน) ส่งออกเป็นไฟล์ PDF ได้
7. ระบบมีขั้นตอนให้ผู้ใช้ตรวจทาน/แก้ไขข้อความถอดเสียง และตรวจทาน/แก้ไข/อนุมัติรายงานที่ AI ร่างก่อนนำไปใช้งานจริง
8. ระบบมีเกณฑ์วัดคุณภาพของผลลัพธ์จาก AI และมีการทดสอบเสถียรภาพของบอท

**ข้อจำกัดที่ระบุไว้ (ควรใส่เพื่อความชัดเจน):** รองรับการประชุมทีละห้องต่อเครื่อง, ออกแบบสำหรับติดตั้งเครื่องเดียว (ต้นแบบสำหรับสาธิต), ไม่มีหน้าผู้ดูแลระบบ/แดชบอร์ดสถิติรวม

## 4. ทฤษฎีและเครื่องมือที่เกี่ยวข้อง

### 4.1 หัวข้อ 3 LLM (หน้า 6) — ย่อหน้า "MeetSync นำแนวคิดนี้มาพิจารณา..."

**เดิม:** "...โดยส่งข้อความทั้งหมดเข้าไปในครั้งเดียวพร้อมสั่งให้สกัดทั้งสรุปมติและภาระงานออกมาพร้อมกัน..."

**แก้เป็น:**
MeetSync นำแนวคิดนี้มาพิจารณาเลือกใช้ Gemini API ในการวิเคราะห์บทสนทนาและร่างรายงานการประชุม โดยบังคับรูปแบบผลลัพธ์ด้วย response schema (วาระ มติ ภาระงาน) หากข้อความมีขนาดไม่เกินเกณฑ์จะส่งในครั้งเดียว แต่หากเป็นการประชุมยาว (เกิน 30,000 ตัวอักษร) ระบบจะแบ่งข้อความเป็นช่วง สกัดบันทึกย่อทีละช่วง แล้วจึงเรียบเรียงเป็นรายงานฉบับเดียว (map-reduce) เพื่อไม่ให้ข้อมูลล้นหน้าต่างบริบท และเพื่อลดความเสี่ยงที่โมเดล "มโน" เนื้อหา ระบบกำหนดให้ทุกมติและภาระงานต้องมีข้อความอ้างอิงที่คัดลอกจากบทสนทนา แล้วตรวจสอบว่าข้อความอ้างอิงนั้นมีอยู่จริง ก่อนแสดงผลให้มนุษย์ตรวจสอบ

### 4.2 เพิ่มหัวข้อใหม่ "การควบคุมคุณภาพผลลัพธ์ของ AI"
AI สามารถให้ผลลัพธ์ผิดพลาดได้ จึงไม่ควรมอบหมายให้ AI สรุปโดยปราศจากเกณฑ์วัด MeetSync ควบคุมคุณภาพ 3 ชั้น
1. **ตรวจอัตโนมัติทุกรายงาน**: ผู้รับผิดชอบต้องอยู่ในรายชื่อผู้เข้าร่วม, วันที่/เวลาต้องอ่านได้และสมเหตุผล, ข้อความอ้างอิงต้องปรากฏใน transcript (เทียบความเหมือน ≥ 80%), ส่วนหัวรายงาน (วันเวลา สถานที่ ประธาน เลขา ผู้มาประชุม) ดึงจากข้อมูลในระบบ ไม่ให้ AI สร้างเอง รายการที่ไม่ผ่านจะแสดงเป็นคำเตือนก่อนอนุมัติ
2. **มนุษย์อนุมัติเสมอ**: รายงานที่ AI ร่างเป็นเพียงฉบับร่าง (มีลายน้ำ "ฉบับร่าง" ใน PDF) จนกว่าผู้ที่ได้รับสิทธิ์จะตรวจแก้และอนุมัติ ระบบเก็บฉบับที่ AI ร่างไว้เทียบกับฉบับที่มนุษย์แก้
3. **ชุดวัดคุณภาพเทียบเฉลย**: ให้คนเขียนเฉลยของการประชุมแล้วเทียบกับรายงานที่ AI ร่าง ด้วยตัวชี้วัดที่คำนวณแบบตายตัว (ไม่ใช้ AI ตัดสิน AI) 9 ตัว พร้อมเกณฑ์ผ่านที่เสนอ

| ตัวชี้วัด | เกณฑ์ผ่าน |
|---|---|
| ครบถ้วนของวาระ | ≥ 80% |
| ความถูกต้องของมติ | ≥ 80% |
| มติที่แต่งขึ้น (วาระที่ไม่มีมติจริงแต่ AI ใส่มติให้) | ≤ 10% |
| ครบถ้วนของงาน / งานที่ถูกต้อง | ≥ 80% / ≥ 80% |
| ผู้รับผิดชอบถูกคน / วันกำหนดถูกต้อง | ≥ 90% / ≥ 90% |
| ข้อความอ้างอิงที่ตรวจไม่พบ | ≤ 20% |
| งานที่ผิดแต่ระบบตรวจไม่พบ | = 0 |

ข้อความคำสั่ง (Prompt) ของ AI เก็บเป็นไฟล์แยกตามเวอร์ชันภายในระบบ และรายงานแต่ละฉบับบันทึกชื่อ Prompt ที่ใช้ ผู้ใช้ทั่วไปไม่ต้องแก้ไขโค้ด

### 4.3 หัวข้อ 5 API และเครื่องมือ (หน้า 7)

**ย่อหน้า Playwright:** เติมต่อท้าย —
เพื่อให้บอททำงานต่อเนื่องในการประชุมที่ยาว ตัวจับคำบรรยายจะล้างแถวคำบรรยายและตัวจับเวลาที่ปิดจบแล้วอย่างสม่ำเสมอเพื่อไม่ให้หน่วยความจำสะสม และมี **Watchdog** ซึ่งเป็นกลไกตรวจสุขภาพของบอททุก 15 วินาที (ตรวจว่าหน้าประชุมยังอยู่ ตัวจับคำบรรยายยังทำงาน และยังเห็นกรอบคำบรรยาย) หากพบความผิดปกติจะติดตั้งตัวจับใหม่หรือเปิดคำบรรยายอีกครั้ง และหากบอทหลุดจากห้อง จะปิดการบันทึกอย่างเรียบร้อย ข้อความที่บันทึกแล้วไม่สูญหาย

**ย่อหน้า Backend (เดิม "Backend พัฒนาด้วย FastAPI ...") → แก้เป็น:**
ระบบแบ่งเป็นสองส่วนที่ทำงานคู่กัน ส่วนที่หนึ่งคือ **บริการบอท** พัฒนาด้วย FastAPI ทำหน้าที่ควบคุมบอท Playwright บันทึกคำบรรยายลงฐานข้อมูลผ่านคิวเขียนเพียงตัวเดียว และรับการเชื่อมต่อ Google Calendar แยกเป็นโปรเซสของตนเอง เพื่อให้บอททำงานต่อเนื่องได้แม้หน้าเว็บถูกรีเฟรชหรือปิด ส่วนที่สองคือ **หน้าเว็บ** พัฒนาด้วย Streamlit สำหรับสร้างการประชุม ตรวจทาน แก้ไข อนุมัติ และส่งออก โดยสื่อสารกับบริการบอทผ่าน HTTP ด้วยโทเคนลับร่วม ข้อมูลทั้งหมดจัดเก็บใน MySQL ...(ย่อหน้าเดิมต่อ)

## 5. อุปกรณ์ — ซอฟต์แวร์ (หน้า 9) เพิ่มไลบรารี

เพิ่มต่อจากข้อ 2.7.7:
- 2.7.8 Streamlit: สร้างหน้าเว็บ (สร้าง/ตรวจทาน/แก้ไข/อนุมัติ) และระบบล็อกอิน Google (OIDC)

- 2.7.12 pandas: จัดการข้อมูลตารางแสดงผลและแก้ไขในหน้าเว็บ
- 2.7.13 itsdangerous: เซ็นโทเคนที่ใช้ระหว่างหน้าเว็บกับบริการบอท
- ข้อ 2.7.1 FastAPI: แก้คำอธิบายเป็น "เฟรมเวิร์กสร้างบริการบอท (REST API)"

## 6. วิธีการที่นำเสนอ (หน้า 10)

**เดิม 6 ข้อ → แก้เป็น 9 ข้อ:**
1. **Login:** ผู้ใช้เข้าสู่ระบบด้วยบัญชี Google ใดก็ได้ผ่าน OAuth 2.0 ระบบบันทึกผู้ใช้และเวลาเข้าใช้งานล่าสุดลงแฟ้ม users (ขอสิทธิ์ระบุตัวตนเท่านั้น แยกจากสิทธิ์ Calendar ซึ่งขอแยกต่างหากต่อท้ายการล็อกอินครั้งแรก)
2. **Setup Meeting & Roles:** เจ้าของการประชุมสร้างการประชุม กรอกลิงก์ Meet หัวข้อ หน่วยงาน ครั้งที่ สถานที่ และรายชื่อผู้เข้าร่วมพร้อมบทบาท (ประธาน เลขา ผู้เข้าร่วม ผู้ไม่มา)
3. **Start Meeting Bot:** สั่งบอท (Playwright) เข้าห้องประชุมและเปิด Closed Captions โดยอัตโนมัติ (ผู้จัดประชุมต้องอนุญาตให้บอทเข้าห้องเอง)
4. **Capture Captions:** ดักจับคำบรรยายสดและชื่อผู้พูด บันทึกลงฐานข้อมูลต่อเนื่องทุกประโยคที่จบ โดยมี Watchdog ตรวจสุขภาพของบอท
5. **Transcript Review:** หลังประชุมจบ ผู้ใช้ตรวจแก้ข้อความ เปลี่ยนผู้พูด ลบช่วงที่ไม่เกี่ยวข้อง รวมชื่อที่ Meet แสดงให้ตรงกับรายชื่อ (เก็บข้อความต้นฉบับไว้) แล้ว **ยืนยัน transcript** (ถ้ายังไม่ยืนยัน ระบบไม่ให้ AI สร้างรายงาน)
6. **AI Minutes Drafting:** ส่ง transcript ที่ยืนยันแล้วเข้า Gemini เพื่อร่างรายงาน (สรุป วาระ มติ เรื่องอื่น ๆ ภาระงาน) พร้อมตรวจสอบผลลัพธ์อัตโนมัติและแสดงคำเตือน
7. **Review & Approve:** ผู้มีสิทธิ์ตรวจและแก้ไขรายงาน แล้วอนุมัติ รายงานที่อนุมัติแล้วถูกล็อก (ยกเลิกอนุมัติเพื่อแก้ไขได้)
8. **Export:** ดาวน์โหลดรายงานเป็น PDF และส่งภาระงานที่มีวันกำหนดเข้า Google Calendar โดยแสดงสถานะการส่ง
9. **View Meeting History:** เปิดดูประวัติการประชุม ข้อความถอดเสียง รายงาน และภาระงานย้อนหลัง

## 7. Flowchart (หน้า 12) — คำอธิบายใต้ภาพที่ 1

**แก้เป็น:** จากภาพที่ 1 ผู้ใช้ล็อกอินผ่านบัญชี Google ระบบบันทึกลงตาราง users จากนั้นเจ้าของการประชุมสร้างการประชุมและกำหนดรายชื่อ/บทบาทผู้เข้าร่วม (บันทึกลงตาราง meetings และ speakers) แล้วสั่งบอทเข้าห้อง Google Meet เพื่อดักจับบทสนทนาสดบันทึกลงตาราง transcript_segments แบบต่อเนื่อง เมื่อจบการประชุม ผู้ใช้ตรวจทานและยืนยัน transcript ระบบส่ง transcript ที่ยืนยันแล้วให้ Gemini AI ร่างรายงาน (สรุป วาระ มติ ภาระงาน) บันทึกลงตาราง summaries, agenda_items และ action_items เป็นฉบับร่าง ผู้มีสิทธิ์ตรวจทาน แก้ไข และอนุมัติรายงาน จากนั้นจึงส่งออกเป็น PDF และส่งภาระงานเข้า Google Calendar

> **ต้องวาดภาพที่ 1 ใหม่:** เพิ่มกล่อง "กำหนดรายชื่อ/บทบาท", "ตรวจทานและยืนยัน transcript", "ตรวจ/แก้ไข/อนุมัติรายงาน" และกล่อง "ส่งออก PDF" ก่อน/คู่กับ Calendar

## 8. Step-by-Step (หน้า 13–14) — แก้เป็นตารางนี้

| ลำดับ | กระบวนการ | รายละเอียด |
|---|---|---|
| 1 | การเข้าสู่ระบบ | ล็อกอินด้วยบัญชี Google (OAuth 2.0/OIDC) ขอสิทธิ์ระบุตัวตนเท่านั้น (openid, email, profile) หลังล็อกอินครั้งแรกระบบชวนให้อนุญาตสิทธิ์ Calendar แยกต่างหาก (ข้ามได้) |
| 2 | บันทึกข้อมูลผู้ใช้ | บันทึกผู้ใช้และเวลาเข้าใช้ล่าสุดลงตาราง users |
| 3 | สร้างการประชุมและกำหนดบทบาท | ป้อนลิงก์ Meet หัวข้อ หน่วยงาน ครั้งที่ สถานที่ และรายชื่อผู้เข้าร่วมพร้อมบทบาทและสถานะ (เข้าร่วม/ไม่มา) |
| 4 | บอทเข้าร่วมและดักจับข้อความ | บอท (Playwright) เข้าห้อง เปิด Closed Captions ภาษาไทย ดักจับข้อความและชื่อผู้พูด พร้อม Watchdog ตรวจสุขภาพ |
| 5 | บันทึกข้อความลงฐานข้อมูล | บันทึกข้อความที่จบประโยคแล้วพร้อมผู้พูดลงตาราง speakers และ transcript_segments ต่อเนื่องระหว่างประชุม |
| 6 | ตรวจทานและยืนยัน transcript | แก้ข้อความ/ผู้พูด ลบช่วงที่ไม่เกี่ยวข้อง รวมชื่อที่ซ้ำ แล้วยืนยัน transcript |
| 7 | ร่างรายงานด้วย AI | ส่ง transcript ที่ยืนยันเข้า Gemini API ให้ร่างรายงานในโครงสร้าง JSON (แบ่งเป็นช่วงถ้าประชุมยาว) ตรวจสอบผลลัพธ์อัตโนมัติ บันทึกเป็นฉบับร่าง |
| 8 | ตรวจ แก้ไข และอนุมัติรายงาน | ผู้มีสิทธิ์ตรวจคำเตือน แก้ไขทุกช่อง แล้วอนุมัติ รายงานที่อนุมัติแล้วถูกล็อก |
| 9 | ส่งออก PDF และ Google Calendar | ดาวน์โหลด PDF ตามแบบฟอร์ม และส่งภาระงานที่มีวันกำหนดเข้า Calendar (มีเวลา = กิจกรรมช่วงเวลา, ไม่มี = เต็มวัน) แสดงสถานะส่ง |
| 10 | เรียกดูประวัติย้อนหลัง | ดูรายการประชุม สถานะ ข้อความถอดเสียง รายงานและภาระงานย้อนหลัง |

## 9. Process (หน้า 15) และคำอธิบาย DFD (หน้า 17–21) — เพิ่มเป็น 8 Process

| Process | ชื่อ | ข้อมูลเข้า → แฟ้มข้อมูล → ข้อมูลออก |
|---|---|---|
| 1 | เข้าสู่ระบบ | email, id_token → users → สถานะเข้าสู่ระบบ |
| 2 | จัดการการประชุมและบทบาท | meet_url, หัวข้อ, หน่วยงาน, ครั้งที่, สถานที่, รายชื่อ+บทบาท+สถานะ → meetings, speakers → คำสั่งเริ่มบอท |
| 3 | ดักจับและจัดเก็บข้อความ | timestamp, speaker, text จากบอท → speakers, transcript_segments |
| 4 **(ใหม่)** | ตรวจทานและยืนยัน transcript | การแก้ข้อความ/ผู้พูด/ลบ/รวมชื่อ จาก Host → transcript_segments (เก็บ original_text), speakers, meetings.status → transcript ที่ยืนยันแล้ว |
| 5 | ร่างรายงานด้วย AI | transcript + รายชื่อ/บทบาท → Gemini → summaries, agenda_items, action_items (ฉบับร่าง + คำเตือนจากการตรวจสอบ) |
| 6 **(ใหม่)** | ตรวจ แก้ไข และอนุมัติรายงาน | การแก้ไขรายงาน, คำสั่งอนุมัติ จากผู้มีสิทธิ์ → summaries (approved_by, approved_at), agenda_items, action_items, meetings.status |
| 7 | ส่งออก PDF และ Calendar | คำสั่งส่งออก → อ่านรายงานที่อนุมัติ → สร้าง PDF / Google Calendar API → อัปเดต action_items (calendar_synced, google_calendar_event_id) |
| 8 | เรียกดูประวัติย้อนหลัง | user_id → meetings, speakers, transcript_segments, summaries, agenda_items, action_items → ประวัติฉบับสมบูรณ์ |

> **ต้องวาด DFD ใหม่:** Context Diagram (ภาพที่ 2) เพิ่ม PDF เป็นข้อมูลออก, Process 2 (ภาพที่ 4), Process 4 ใหม่, Process 5 (เดิมภาพที่ 6) เพิ่มรายชื่อ/บทบาทเป็นข้อมูลเข้า, Process 6 ใหม่, Process 7 (เดิมภาพที่ 7) เพิ่ม PDF และเปลี่ยนเลขกระบวนการประวัติเป็น 8

## 10. โครงสร้างฐานข้อมูลและ Data Dictionary (หน้า 22–29)

**RDM:** เพิ่มตาราง **agenda_items** (FK → summaries) และเพิ่มคอลัมน์ตามด้านล่าง (ตารางเดิม 6 ตาราง + ตารางใหม่ 1 ตาราง = **7 ตารางข้อมูล**)

ความสัมพันธ์: users 1—N meetings (owner_user_id) · meetings 1—N speakers · meetings 1—N transcript_segments · speakers 1—N transcript_segments · **meetings 1—1 summaries** · summaries 1—N agenda_items · summaries 1—N action_items · users 1—N summaries (approved_by)

### ตารางที่ 1: users — **เพิ่ม** `calendar_token`
| Element | Description | Data Type | Permissible / Key |
|---|---|---|---|
| calendar_token | โทเคนเชื่อมต่อ Google Calendar ของผู้ใช้ (JSON) ใช้สร้างนัดหมายในปฏิทินของผู้ใช้คนนั้น | LONGTEXT | NULL ได้ (ยังไม่เชื่อมต่อ) |

(คอลัมน์เดิม user_id, google_sub UNIQUE, email, name, picture, created_at, last_login_at คงเดิม)

### ตารางที่ 2: meetings — **เพิ่ม** และ **แก้ status**
| Element | Description | Data Type | Permissible / Key |
|---|---|---|---|
| owner_user_id | เจ้าของการประชุม | INT | FK (users.user_id), NULL ได้ |
| venue | สถานที่ประชุม | VARCHAR(255) | NULL ได้ |
| scheduled_at | วันเวลานัดหมายประชุม | DATETIME | NULL ได้ |
| meeting_no | ครั้งที่ประชุม (เช่น 3/2569) | VARCHAR(50) | NULL ได้ |
| org_name | ชื่อหน่วยงาน | VARCHAR(255) | NULL ได้ |
| **status (แก้)** | สถานะตามขั้นตอนทำงาน | VARCHAR(20) | `scheduled`, `recording`, `transcript_review`, `transcript_verified`, `draft`, `approved` (เดิม `in_progress`, `completed`) |

### ตารางที่ 3: speakers — ผู้เข้าร่วมประชุม (1 แถวต่อ 1 คนต่อการประชุม) **เพิ่ม**
| Element | Description | Data Type | Permissible / Key |
|---|---|---|---|
| meet_alias | ชื่อที่ Google Meet แสดง (กรณีต่างจากชื่อในรายชื่อ ใช้จับคู่อัตโนมัติ) | VARCHAR(100) | NULL ได้ |
| email | อีเมลผู้เข้าร่วม (ใช้ให้ประธาน/เลขาเข้าตรวจได้ และเพิ่มเป็นผู้ร่วมงานใน Calendar) | VARCHAR(255) | NULL ได้ |
| role | บทบาทในการประชุม | VARCHAR(20) | `chair`, `secretary`, `attendee` (ประธาน/เลขามีได้คนเดียวต่อการประชุม) |
| attendance | สถานะการเข้าประชุม | VARCHAR(10) | `invited`, `present`, `absent` |
| source | ที่มาของรายชื่อ | VARCHAR(10) | `registered` (ลงทะเบียนล่วงหน้า), `meet` (พบจาก Meet) |

(display_name ขยายความ: ชื่อที่ใช้แสดงในรายงาน)

### ตารางที่ 4: transcript_segments — **เพิ่ม**
| Element | Description | Data Type | Permissible / Key |
|---|---|---|---|
| original_text | ข้อความต้นฉบับที่บอทจับได้ก่อนถูกแก้ไข | TEXT | NULL = ไม่เคยแก้ |
| edited_at | วันเวลาที่แก้ไขล่าสุด | DATETIME | NULL ได้ |
| deleted | ช่วงที่ถูกลบ (ลบแบบซ่อน กู้คืนได้ ไม่ส่งให้ AI) | BOOLEAN | 0 / 1 |

หมายเหตุ: 1 แถว = 1 ประโยคที่จบแล้ว บันทึกทันที ส่วนการแสดงผลจะจัดกลุ่มประโยคต่อเนื่องของผู้พูดคนเดียวเป็น "ช่วงพูด" เพื่อให้อ่านง่าย

### ตารางที่ 5: summaries (รายงานการประชุม 1 ฉบับต่อ 1 การประชุม) — **เพิ่ม**

| edited_at | เวลาที่มนุษย์แก้ไขล่าสุด | DATETIME | NULL ได้ |

## 11. ประโยชน์ที่คาดว่าจะได้รับ (หน้า 30) — เพิ่มข้อ

5. ได้รายงานการประชุมในรูปแบบที่นำไปใช้งานได้จริง โดยมีมนุษย์ตรวจทานและอนุมัติ
6. ได้แนวทางและเครื่องมือวัดคุณภาพของผลลัพธ์ที่ AI สรุปจากการประชุมภาษาไทย

## 12. การทดลองเบื้องต้น (หน้า 30–31)

**ข้อ 1–3 เดิมคงไว้** (ผลทดลองจาก Meet จริง/Gemini/Calendar บนต้นแบบก่อนปรับปรุง) แต่ให้เพิ่มวงเล็บว่า "(ทดลองบนต้นแบบก่อนปรับปรุง)" และ **ข้อ 4 เดิม** (หน้า /login ของเว็บเก่า) ให้แก้เป็น:

4. **ระบบ Login ด้วย Google (Streamlit)** — `[ใส่ผลที่ทดสอบจริง: หน้า consent ของ Google แสดงเฉพาะชื่อ/อีเมล/รูปโปรไฟล์ แล้วขึ้นหน้าชวนอนุญาต Calendar แยกต่างหาก]`

**ข้อใหม่ที่ทำจริงแล้ว (ระบุได้):**

5. **ทดสอบอัตโนมัติ** — มีชุดทดสอบมากกว่า 130 รายการ (ฐานข้อมูล ชั้น service บริการบอท การตรวจผลของ AI การส่งออก Calendar ชุดวัดคุณภาพ และหน้าเว็บ) ผ่านทั้งหมด และมีการทดสอบด้วยเบราว์เซอร์จริงตลอดสายงาน (สร้างประชุม → บอท → ตรวจ → AI ร่าง → แก้ไข → อนุมัติ → PDF) ผ่านครบ 30 ขั้นตรวจ โดยใช้บอทและ AI จำลอง
6. **ทดสอบตัวจับคำบรรยายกับ Meet จำลอง 5 นาที** — จับคำพูดที่พูดทั้งหมด 64 ประโยคได้ครบ ข้อความไม่ตรง 0 JS heap เปลี่ยน 0.7 → 0.8 MB, จำนวน DOM nodes และ event listeners ไม่เพิ่ม (เป็นการทดสอบตรรกะของตัวจับด้วยหน้า Meet จำลอง ไม่ใช่ Meet จริง)
